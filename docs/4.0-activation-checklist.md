# Skotiq 4.0 — Activation Checklist (the 3 external steps)

4.0 is **code-complete and gate-green**. Three things require accounts/hardware that live outside the codebase. Each is built to **drop-in-ready** — the software activates the moment you supply the missing piece. Until then, everything is testable (mock paths) and the rest of the app is unaffected.

---

## 1. iOS release (Apple Developer account + a Mac)

The iOS companion (`apps/mobile`) is **build-ready** — Info.plist, entitlements, the APNs registration code, and the Dart token plumbing are all in place; the project's structural integrity was verified. It cannot be **built or signed** here (iOS requires macOS + Xcode + a paid Apple Developer Program membership).

**Do:** follow **`docs/ios-release-setup.md`** — set the signing Team, enable the Push Notifications / Background Modes / App Groups capabilities in Xcode, create the `group.com.skotiq.app` App Group, add the Live-Activity/watch/AppIntents extension targets, submit the **Critical Alerts** entitlement request to Apple (text in `apps/mobile/ios/CRITICAL_ALERTS_SETUP.md`), then `flutter build ios --release` → Archive → TestFlight.

**Until done:** Android ships normally; iOS users wait for the TestFlight build.

---

## 2. Live cellular push (Firebase project + Apple APNs key)

The server-side **FCM + APNs delivery is fully implemented** (`packages/skotiq_remote_protocol/lib/src/push/`) and unit-tested via a mock — but real cloud delivery needs credentials.

**Do:**
1. **Firebase** — create a project, add the Android app (`google-services.json`), generate a **service-account JSON** (for FCM HTTP v1).
2. **Apple** — create an **APNs token key (`.p8`)** in the developer portal; record the Key ID, Team ID, and Topic (`com.skotiq.mobile`).
3. Drop a **`push_config.json`** into the desktop app-support dir pointing at those two secret files (shape documented in the push code + brief); restart.
   - *(Android client token acquisition via `firebase_messaging` is intentionally NOT in the build yet — it hard-fails without `google-services.json`. Add the plugin + that file when Firebase exists; the server endpoint `/api/push/register-token` is already waiting.)*

**Until done:** **LAN/Wi-Fi push already works** (the existing HMAC UDP path). Only *cellular/off-network* delivery waits on these keys. `push_config.json` / `*.p8` / `*service-account*.json` are gitignored.

---

## 3. On-sky validation (a real telescope + a clear night)

Every native algorithm (registration, integration, color calibration, drizzle, deconvolution, the Night-Doctor detectors, the marginal-SNR optimizer) is **synthetic- and integration-tested**, but has **never run on real photons**. This is the one thing no amount of code can substitute.

**Do:** drive a real multi-sub night through the morning-report pipeline; confirm registration RMS, real satellite-trail rejection, color-calibration accuracy, and the Night-Doctor diagnoses against ground truth; tune the **defensible-default** thresholds (weight exponents, Night-Doctor trip points, drizzle pixfrac, deconvolution regularization — all exposed as knobs) with the real data.

**Until done:** the smart-finishing features are sound and shippable; treat the first clear night as a tuning/validation pass, not a regression risk to the rest of the app (every finishing step is fail-soft).

---

**Summary:** ship 4.0 to your tester group now (desktop + Android, LAN push, the full morning report and autopilot). Flip on iOS, cellular push, and the tuned algorithm thresholds as the three pieces above land.
