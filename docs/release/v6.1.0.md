# Skotiq 6.1.0 — Reliability

## Summary

6.1.0 is a reliability release on top of 6.0.0. It closes two ship-blockers,
fixes roughly 92 verified defects across twelve areas of the app, and teaches
the device simulators how to fail so the error paths above them can actually be
exercised without a rig.

The two ship-blockers were both silent, which is what made them dangerous.

**Your image library could be quarantined for no reason.** The database
integrity check treated *any* open-time SQLite error as corruption: a lock held
by another process, a read-only file, a transient I/O error. When that happened
it moved your database aside as `skotiq-corrupt-<timestamp>.db` and let a
blank one take its place. Nothing looked wrong — the app simply opened empty.
The check now classifies by SQLite result code, so only genuine corruption
(`SQLITE_CORRUPT`, `SQLITE_NOTADB`, or a failing `PRAGMA integrity_check`)
quarantines anything; a hot rollback journal left by a crash is now replayed
rather than destroyed. A real database quarantined by an earlier build was
recovered during this work with all 182 captured frames intact, and the recovery
dialog now re-checks a quarantined file and tells you plainly when it was never
corrupt, with a one-click restore.

A single-instance lock is now taken beside the database, so two copies of
Skotiq can never contend for it — which is what produced the false
corruption in the first place.

**The mosaic project screen never loaded.** `/mosaic/:id` showed an infinite
spinner with no chrome and no way back, over a rebuild loop burning roughly
fourteen times the CPU it should.

## What's verified

Every automated gate is green: 9,716 Dart tests across eleven packages, 420
Rust bridge tests, 694 Rust sequencer tests, zero analyzer errors or warnings,
and the format, placeholder, comment and version-consistency audits.

Every fix was re-checked by an independent verification pass that re-derived
each root cause instead of trusting the fix. That pass **rejected 7 of 11 fix
batches on first submission** — the recurring failure was moving a defect rather
than removing it. Each was reworked until the defect was gone, and every new
regression test was checked by reverting its fix to confirm the test fails.

The Windows archive published here was audited directly: downloaded from this
release, SHA-256 verified, extracted, and checked against the required-file
manifest — 830 files, nothing missing, nothing disallowed.

**Not verified in this release:** nothing was validated on real hardware or on
sky, and the app was never launched on Windows (the audit covers what is in the
archive, not how it behaves). Remote access from a second physical device
through a real router was not tested. See `docs/known-limitations.md`.

## What's verified — scoped capability claim

This claim is repeated word for word in the README and in `docs/known-limitations.md`.

> **6.1.0 adds no new hardware validation.** The most recent real-hardware evidence remains the 6.0.0 Windows bench run between 22 and 26 July 2026 against an ASCOM Pegasus NYX-101 mount, a native ZWO ASI1600MM-Cool camera, and a ZWO EFW filter wheel, alongside a simulator instance. Camera connect, cooling, exposure, and image download are exercised on that hardware. **The mount was never commanded to move**, so slew, sync, park, unpark, homing, and meridian flip are unexercised on real equipment. **No frame was taken under a real sky** — the acquisition path is validated, the sky is not. 6.1.0 changes guiding correction behaviour and native target scoring; both are unit-tested only and **neither has been run on sky**. The web dashboard and the Android companion were driven against a running host, but a second physical device on a real LAN with a firewall in the path was not tested for either release. Fully-unattended **headless** acquisition and a full-night soak are **not** verified and must be supervised. **Linux** is early testing; **macOS** and **iOS** are unbuilt, untested, and ship no artifact. Every other device path — switches, domes, covers, and the remaining vendor SDKs — is **capability-gated**: present in the app, but not a support guarantee until it is verified on your rig.

## Guiding and target selection changed

Two fixes change what happens on a real run, not just what is displayed.

**The built-in guider was ignoring small errors forever.** Corrections shorter
than the mount's minimum pulse were discarded, so the mount's pulse floor became
the effective dead band instead of the guider's own declared noise floor
(0.15 px). Against a one-directional drift — periodic error, polar
misalignment — a proportional loop with that dead band parks at a standing
offset and never works it off. Sub-minimum demand is now carried across frames
until it can be issued as one pulse the mount will honour. Noise cannot
accumulate into a pulse, and the carry is bounded.

**The scheduler preferred a bright moon.** In the native target scorer,
`score_moon_distance` returned a flat perfect score for any separation past its
threshold, so a full moon at 120° scored higher than a new moon at the same
separation. The Dart copy had been fixed months ago; the Rust twin — the one the
in-run scheduler actually calls — had not, and the parity test only checked a
different function. Both are now correct and the parity check covers it.

Both changes are unit-tested only. Run a supervised night before relying on
either unattended.

## Simulators can now fail

The device simulators could only succeed. Across 1,753 lines there were nine
error returns, and every one was a "you forgot to connect" gate — nothing could
model a device that connects, answers, and then misbehaves. That makes a green
test suite much weaker evidence than it looks.

6.1.0 adds fault injection across fifteen operation keys, armable in a release
build with the `SKOTIQ_SIM_FAULTS` environment variable and no rebuild.
Triggers cover one-shot, N-times, always, works-then-dies-after-N, every-Nth
(intermittent), and a seeded probability that replays exactly from its seed.
Effects cover driver errors, the real ASCOM `0x80020009` not-implemented
failure, mid-session disconnects, slow responses, the INDI download timeout, a
stalled mechanism, and focuser backlash.

Stall and backlash deliberately report **success**. A mount or filter wheel that
accepts a command and never arrives is the failure that costs a night precisely
because nothing reports an error — only a timeout or a position re-read can
catch it. Returning an error there would have tested the easy path.

## Also fixed

- The headless API advertised command/event correlation that was entirely
  inert: no handler was ever given a correlator, so responses carried no
  `commandId` and every event reported `correlatingCommandId: null`.
- The dashboard clock and status bar asserted a precise local sidereal time
  when no observing site was set, showing Greenwich's as though it were yours.
- "Last checked" on equipment cards was pinned at "0s ago" forever, because its
  refresh ticked at exactly the poll period it was measuring.
- The Plan Tonight moon filter applied a 30° limit you never chose if you opened
  it and pressed Apply.
- The coordinate-grid switch in the planetarium turned on and drew nothing.
- Capture and stretch controls were clipped and unreachable at common window
  widths, including 1280×800.
- An undersized touch target on the analytics tab strip (24×30 dp, below the
  48 dp Android minimum) at the screen edge.
- The first-run tour pointed at a "Target Queue" tab that no longer exists.

Android ships one APK per ABI rather than a universal build; `arm64-v8a` is the
right one for essentially every current phone or tablet. Every application
artifact has a matching `.sha256` file.

Windows is unsigned and Android is debug-signed, so install warnings appear.
Vendor SDK binaries are not redistributed, so native device paths need vendor
support installed (ASCOM, Alpaca, INDI). The Linux archive targets an
ubuntu-22.04-class glibc floor with native dependencies bundled. There is no
macOS artifact.

## Upgrading

Back up your database directory first, then close any running copy — the new
single-instance lock will refuse a second copy against the same database.
Replace the bundle and launch once to confirm the version reads 6.1.0 and your
library and equipment profiles are present. If an earlier build quarantined your
database, the recovery dialog will offer to restore it.

Nothing in 6.1.0 writes a schema an unmodified 6.0.0 cannot read, so rolling
back is re-extracting the 6.0.0 archive. The `skotiq.db.lock` file is inert
to older builds.
