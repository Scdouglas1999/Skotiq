# Skotiq 4.2.0

4.0 made it possible to run your rig from the couch; 4.1 made the whole thing
feel solid. 4.2 is the **sequencer release**: a top-to-bottom hardening of the
acquisition planner and the live run experience, plus an architecture pass that
makes the Dart/Rust boundary something the build enforces rather than trusts.

## What's verified

Skotiq is verified on **Windows**, where the desktop app drives ASCOM/Alpaca
cameras, focuser, filter wheel, and PHD2, with plate-solving and planning. Remote
**monitoring and planning** over the LAN — from the web dashboard and the Android
companion — are verified. Fully-unattended **headless** acquisition on real ASCOM
hardware is **still being hardened** and should be supervised. **Linux** is in
early testing; **macOS** builds in CI with no hardware soak. Every other device
path is **capability-gated** — present in the app but not a support guarantee
until verified per rig.

The 4.2 sequencer changes are verified at **static-analysis + unit/widget-tested
+ (where applicable) simulator-tested** level, on top of the 4.1 real-hardware
baseline; they were not re-run on a physical rig. The honest, level-by-level
record is in [`release-evidence/4.2.0.md`](../release-evidence/4.2.0.md).
Supervise your first nights.

## The sequencer, told straight

The biggest win is that the sequencer's own numbers now match reality:

- **Progress and ETA stopped lying.** The completion bar and time-remaining are
  now loop-aware and count Smart-Exposure plans — a `Loop ×50` over a 10-frame
  node no longer hits 100% at frame 10, and a Smart-Exposure-only run actually
  shows progress. The per-frame ETA uses real exposure cadence instead of
  wall-clock that included slews and autofocus.
- **One honest time estimate.** The per-node duration chip, the timeline, and
  the run-dashboard total now share a single overhead model sourced from your
  settings, so they agree.
- **No ghost runs.** A failed start now rolls back cleanly instead of leaving the
  UI claiming it's imaging.

## Building & running a sequence

- **The tree collapses by mouse and touch** (it was keyboard-only); drag-to-
  reparent now refuses to create a cycle; snippets insert enabled instead of
  silently disabled.
- **Skip the current target**, not just the current step — the move you want when
  clouds settle over one object.
- **Glance mode** bumps secondary status text up for reading across a dark room,
  and an **app-wide running-sequence mini-player** keeps pause/stop/skip reachable
  even when you navigate away from the sequencer.
- **Library upgrades:** tags, favorites, version history with restore, a real
  **diff against the previous run** (it used to compare a sequence to itself),
  and a faster list that no longer loads every saved sequence's full tree.
- **Multi-filter mosaics** — each panel can image a full per-filter set.

## Typed photometry events

Photometry progress (frames, cadence breaks, summaries) is now carried as
first-class typed events from the Rust core through the bridge, so the light-curve
panel binds real fields instead of parsing strings — following the same typed-
payload pattern introduced for grading/scheduler progress.

## Architecture: the bridge boundary is now enforced

The project's rule that only `skotiq_core` talks to the Rust bridge is now a
build gate (`audit:bridge-boundary`). The real UI leaks were relocated behind
`ImagingBackend` / `GuidingBackend` / `DeviceBackend` role seams (image stretch /
FITS read, the PHD2 probe, and dome/cover-calibrator control), and run-dashboard
event consumers now read event types re-exported from core. The whitelist holds
only legitimate exceptions. Two oversized handlers were split by responsibility.

## Storage

Schema **v49** adds, additively: per-run sequence snapshots (powering the real
run diff), sequence tags/favorites, a sequence-versions table, and per-session
diagnostics so a historical session report shows that run's data, not the live
one. The migration has synthetic regression coverage; verifying it against a real
older database remains an owner checklist item.

## Carried over

The on-sky caveat still stands: the finishing and photometry algorithms are
tested against synthetic data and are internally consistent, but their accuracy
hasn't been validated against real frames — shoot a field with published
comparison-star magnitudes before submitting measurements. Fully-unattended
headless runs should be supervised. iOS and live cellular-push delivery still
need a Mac/Apple Developer account and your own Firebase/APNs keys.
