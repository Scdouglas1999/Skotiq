# Skotiq 9.3.0

Update the imaging host to 9.3.0 first, then update each linked desktop or mobile client. Skotiq requires both ends of a Link connection to run the same release. The desktop and companion apps are build 41.

This release is mostly about the Android app. Its screens were desktop panels stacked into one column; they now use a phone's space, work on small phones, on their side and on tablets, and the setup from a fresh install can be done from the phone. Several things that did not work at all from a phone now do. A few of the fixes are on the host and help every linked client.

## Things that did not work from a phone

- A phone could never start a run. The pre-flight check looked for the capture folder on the phone instead of on the imaging computer. The host still refuses a run when its own folder is missing.
- Opening a saved frame failed with an error about the native library. The host now draws the frame and sends it to the phone, the way the live view already worked.
- After the host crashed or restarted mid-run, the phone never offered to resume the run, so it could not be recovered from the phone. The offer now appears, also when the host comes back within half a minute and the phone reconnects on its own.
- An equipment profile made on the phone never reached the host's run engine and built-in guider. The built-in guider refused to connect until the host was restarted, and edits to the active profile from a phone went stale the same way.
- Session frames asked the host for every thumbnail of the night at once. With a thousand frames the host turned the requests away and no thumbnail showed. Only the thumbnails on screen are loaded now.
- "Use this phone's location" gave up on the GPS after 3 seconds, a time that also had to cover the permission prompt, and fell back to a city-level guess from the internet address. It now waits for the permission answer and gives the GPS 30 seconds.
- Coming back to the app after a minute or more showed the connect screen with "No answer from" the host for ten seconds or longer. It now stays on the screen you left and reconnects within a couple of seconds.
- Pairing had a "full control" switch that did not show, while setup told you to pair again with full control.

## Getting set up

- The connect screen leads with scanning the pairing QR code. Remote options (Tailscale, relay) are grouped under "Away from home", and discovery messages say where the app is looking rather than naming protocols.
- The pairing dialog names the computer it found, offers to scan the QR code, and pairs with full control by default (there is a switch to turn it off for a phone you lend to someone). If you close it to go and get the code, the connect screen keeps the computer it found, with a Pair button.
- First-run setup can create the equipment profile on the phone. Before, it sent you to another computer, which a headless rig does not have.
- The capture folder picker opens a folder when you tap it, can make a new folder on the imaging computer, says when a folder is empty, and leads back to the top level.
- The profile editor on a phone shows a name field only for slots that have a device, so it is about half as long, and picking a device no longer opens the keyboard. It says when the built-in guider has no focal length to work from.
- Location on a phone puts "Use this phone's location" first, with a short note on what the lookup sends.
- The phone no longer asks for notification permission the moment it opens. Once linked, a banner says what alerts are for and asks; Tonight's "Before you start" list shows Alerts while they are off.
- The launch screen is dark instead of white.

## Using it at night

- Each screen's own header is the top bar, with the link status at its end, so there is no second bar above it. Turned on its side, a phone gets a navigation rail on the left; tablets get the rail and Tonight's two-column layout.
- Tonight before a run opens with the plan and the readiness list. Its charts are tall enough to read, and run warnings fold into one line you can open.
- Imaging sizes the live frame to the image so the controls get the rest, and on a phone on its side the controls sit beside the frame.
- The Plan list fills the screen and opens a target's details in a sheet.
- Pre-flight and other tall dialogs use the whole screen on a phone.
- Settings fields sit under their titles at full width.
- Autofocus progress is a small pill rather than a window over the screen.
- The running Sequencer shows one progress bar that fits a phone. A floating card that repeated the same numbers over the plan is gone.
- The exposure count can be typed. Millisecond exposures read "5 ms" instead of "0 s" or "1s".
- One notification per finished or failed run, instead of two.
- The mount alert, tab strips and page titles fit a 360 dp phone.

## Host and other clients

- `GET /api/images/<id>/jpeg` returns a saved frame through the display stretch as a JPEG, with its size in `x-image-meta`. `maxWidth` bounds the bitmap.
- `POST /api/files/validate` accepts `"create": true` to make the folder first, inside the same allowed folders.
- Saving the active profile through the API now updates the run engine's copy, as the host's own editor does.
- The built-in guider's "no profile" message says what it actually lacks.

## Not tested

None of this has run on the rig or on a real phone. It was tested on an Android emulator against a headless host with simulated equipment, with every action checked on the host. Not tested: a real phone's GPS and notifications, scanning a real QR code, iOS, and the release APK. The phone's reconnect and resume logic is covered only by those emulator runs, not by automated tests.

A fresh headless rig still needs someone at the computer to install a plate solver; the phone cannot install one. Until then, Image tonight and centering do not work from the phone.
