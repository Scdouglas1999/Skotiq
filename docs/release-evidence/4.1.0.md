# Release Evidence — 4.1.0

This document records what was actually exercised for the 4.1.0 release, and at
what level. It exists so claims in the README and release notes can be traced to
real testing rather than to code presence. **A vendor name or capability in the
codebase is not a support guarantee** — only the rows below marked *real hardware
tested* were run against a physical rig.

Evidence levels, from weakest to strongest:

- **Code implemented** — written and compiles/analyzes clean, no runtime check.
- **Unit tested** — covered by an automated `flutter test` / `cargo test` case.
- **Simulator tested** — exercised against a simulated device or generated input.
- **Real hardware tested** — run against the physical device named below.
- **Not yet validated** — in scope but not exercised at any level above.

## Real hardware tested — verified working

These ran on the rig above and behaved correctly.

- **Headless server lifecycle:** boot, LAN bind, token auth, mDNS `_skotiq._tcp`
  discovery, 6-word pairing (`start`→`verify`) and one-tap `lan-claim`.
- **Camera capture (ASI1600):** connect, status, a 2 s 16 MP exposure, JPEG
  download, and a cooling cycle. *Caveat: the driver degraded over a long
  headless session — see "known broken" below (B18).*
- **Focuser (EAF):** connect, real telemetry, single absolute moves.
- **Filter wheel (EFW):** connect, 8 named slots read back. *Caveat: position
  set is a headless no-op — see B5 below.*
- **PHD2:** connect.
- **Capture → FITS pipeline:** a real 2 s frame written as a valid 32.7 MB,
  4656×3520, 16-bit FITS to disk and re-read via `fits-dimensions`. Sound end to
  end.
- **Plate solving:** ASTAP invoked as an async job (queue → progress →
  succeeded, ~7.4 s), with a graceful no-solution on a starless test frame.
- **Read/data API:** ~26 read-only endpoints (science, calibration, session,
  histories, stacking, plugins, weather, safety, guider, cloud-motion) returned
  sane payloads; web dashboard, run-watch, and pairing UIs rendered.
- **Desktop GUI app (owner-confirmed):** the same camera, mount, focuser, and
  filter-wheel operations that fail in *headless* mode work in the desktop GUI
  app. The headless failures below are headless-mode/COM-pump issues, not device
  or pipeline faults.

## Real hardware tested — known broken or not yet reliable (headless mode)

Found on the rig; these are why headless unattended acquisition is **not** yet a
release guarantee. All are headless ASCOM/COM-session issues; the desktop GUI
path works.

| ID | Symptom | Status |
| --- | --- | --- |

| B18 | Camera driver degrades mid-session; `StartExposure` fails until reconnect | Fix implemented (message pump), runtime-pending |
| B5 | Filter-wheel set-position returns ok but never moves | Fix implemented (message pump), runtime-pending |
| B4 | Camera gain/offset SET faults `0x80020009` (expose/cooling are fine) | Fix implemented (message pump), runtime-pending |

## Unit tested

- **Settings persistence round-trip:** a 139-field property test
  (`packages/skotiq_core/test/providers/app_settings_stored_roundtrip_test.dart`)
  proving `_settingsFromStoredMap(_storedMapFromState(s)) == s` — no field lost,
  mis-keyed, or mis-encoded. Plus 26 settings tests (round-trip + bridge sync +
  remote coverage).
- **Headless handlers:** `update_handlers` 18/18, catalog 8/8.
- **Scheduler astronomy:** altitude/airmass, rise-set, transit
  (`alt = 90 − |lat − dec|`), hours-above-horizon verified numerically.
- **Rust fixes:** `cargo check` / `cargo test` on the LX200 serial-handle fix and
  the ASCOM wrapper changes (the bridge crate's Windows COM paths are verified
  via an isolated `cargo check --target x86_64-pc-windows-msvc`; the full crate
  cannot be cross-built from Linux).

## Simulator / generated-input tested

- **Sequencer engine:** a hand-built native `SequenceDefinition` (Delay +
  Notification nodes) loaded, started, and the executor entered the Delay node
  with correct strict schema validation. The engine runs; what is *not* yet
  reliable headless is the device I/O it drives (B2/B5/B18).
- **Plate solver:** ASTAP exercised on a starless test FITS (graceful
  no-solution path).
- **Planning generators:** mosaic (3×3 panel layout, per-panel RA spacing,
  area/time estimates), flat-wizard sequence generation, and the linear
  temperature-compensation focus-model fit all validated on computed inputs.

## Code implemented — not yet validated on hardware

- The headless ASCOM/COM reliability fixes (STA message pump for B2/B4/B5/B18,
  the LX200 serial-handle leak fix for B3, the always-on `/api/system/version`
  route for B8) are compile-checked and unit-checked but **await a Windows rig
  rebuild** to confirm at runtime.
- The DB-backed headless settings persistence (B16) is unit-verified by the
  round-trip test; the end-to-end POST→DB→GET path still wants the rig.

## Not yet validated

- A full **unattended headless night, end to end, on real hardware** (the four
  headless reliability fixes above must be runtime-confirmed first).
- **Linux** hardware soak (Linux is in early testing; the appliance/native-SDK
  device paths are package- and host-specific, see
  [`supported-hardware-by-platform.md`](../supported-hardware-by-platform.md)).
- **macOS** at any hardware level (builds in CI; no signed artifact, no soak).
- Native SDK camera/mount paths beyond the ASCOM-backed ASI1600/EAF/EFW above.

## Verdict

The **planning, capture, FITS, plate-solving, and data layers are solid**, and
the **sequencer engine itself runs**. Remote **monitoring and planning** over the
LAN work well today. Remote **autonomous acquisition** on the headless Windows
rig is **not yet reliable** and is the focus of the post-4.1.0 hardware-hardening
work. Supervise early nights.
