# Live-rig findings — 2026-08-09

First hardware validation in this campaign. Rig: ZWO **ASI1600MM-Cool** and **ASI178MM** on
`Sean-Laptop` (192.168.1.50), current tree built on the machine (6.1.0 build 25) and driven
headless through an SSH tunnel. Daytime, no slews.

Every item below was **reproduced on the running app before being written down**, per the owner's
rule. Where the app's answer is compared against ground truth, the ground truth comes from talking
to the ASCOM driver directly with a standalone PowerShell COM probe (`C:\src\ascomprobe.ps1`), not
from reading Skotiq's source.

## L1 — `?deviceType=switch` reports zero switches on a rig with six *(fixed)*

`GET /api/devices?deviceType=switch` → `{"devices":[]}`.
`GET /api/devices?deviceType=switch_` → six devices: PegasusAstro Switch 1/2/3, both JustAHub
switches, and Simulated Power Switch.

`DeviceType.switch_` carries a trailing underscore only because `switch` is a Dart reserved word,
and that artefact had leaked into the wire vocabulary. No client guesses `switch_`.

**The general case is worse than the instance.** `?deviceType=totalNonsense` also returned
**HTTP 200 `{"devices":[]}`** — an unparseable type fell through to an empty list, so the endpoint
told the caller authoritatively that the rig had no such hardware when the truth was that it had
not understood the word. Every sibling handler in this API already rejects an unparseable type with
`400 invalid_request`.

Fixed in `device_type_parser.dart` (accept the natural spelling for reserved-word members) and
`device_discovery_handlers.dart` (400 with the valid list instead of a silent empty result).
`apps/desktop/test/headless_api/device_type_parser_test.dart` covers it, including a guard that the
vocabulary cannot become ambiguous if a `foo` is ever added beside a `foo_`.

Note this would have reproduced against the **simulator** too — `Simulated Power Switch` is in that
list of six. It survived a year of audits because nobody had asked that endpoint for a switch by
its obvious name, which is what a denominator catches and exploration does not. Those 577 API
routes only entered the coverage ledger today.

## Not findings — checked and dismissed

* **`recommended-settings` all null.** `unityGain`, `hcgGain`, `defaultOffset` and
  `recommendedCoolingSetpointC` are all null for the ASI1600MM. This is **correct**:
  `native/src/camera.rs:197` states that these come from the **vendor SDK** and that returning all
  `None` "is the honest answer for cameras whose SDK genuinely doesn't expose unity gain — callers
  MUST NOT fabricate a value". The connection here is ASCOM, which exposes none of them. Worth a
  separate test via the native ZWO SDK path, since `ASICamera2.dll`, `EFW_filter.dll` and
  `EAF_focuser.dll` are all in the bundle yet camera discovery returned no `native` entries.
* **`0x80020009` on connect.** Reproduced before the hardware was plugged in, and it was honest —
  the driver was registered but no camera was attached. See the environment note below.
* **The device-type filter is ignored.** My own harness sent `?type=` instead of `?deviceType=`
  and got all 67 devices back for every type. The API was right; the harness was wrong.

## Environment notes worth keeping

* **ASCOM discovery enumerates registered *drivers*, not present *hardware*.** With nothing plugged
  in, the rig still advertised 5 cameras, 7 rotators and 6 switches. Any conclusion drawn from a
  discovery list needs that caveat.
* **A reimaged Windows box keeps its ASCOM registrations but loses vendor USB drivers.** Before the
  cameras were re-seated, the ASI1600 appeared as `WestBridge`, `USB\VID_04B4&PID_00F3`, problem
  code **28** (no driver) — a Cypress FX3 in bootloader mode, i.e. a ZWO camera that never got its
  firmware loaded. The app's connect error at that moment was
  `SDK error: Failed to set property Connected: Exception occurred. (0x80020009)`, which is
  accurate and useless. Windows already knew the device had problem code 28; an app that checked
  could say so. **Candidate product finding, not yet written up** because the right message depends
  on distinguishing not-plugged-in from in-use-by-another-app from driver-broken.
* **Win32-OpenSSH kills the process tree when the session closes**, so an appliance started with
  `Start-Process` over SSH dies immediately. Run it in the foreground of a long-lived SSH session.
* **Windows Firewall blocks 8080 inbound**; an SSH `-L` tunnel avoids needing a firewall rule.
* **`flutter build windows` does not stage the native DLLs.** `scripts/stage_windows_release.ps1`
  exists for exactly that and I skipped it, which is why the first launch died with the bridge's own
  (excellent, specific) "bridge library older than the Dart build" error. Vendor SDK DLLs need
  `-IncludeVendorSdks`, and on this machine they came from the shipped 6.0.0 bundle.

## L4 — the app reports a phantom device as "connected" *(P0 for unattended operation; fix written, not yet validated on hardware)*

**The single most dangerous thing found so far.** The owner does not own an ASI mount — only the
driver is installed, because ASCOM ships drivers independently of hardware. Connecting to it:

```
POST /api/devices/connect {"deviceId":"ascom:ASCOM.ASIMount.Telescope","deviceType":"mount"}
  -> {"status":"connected", ...}

GET  /api/mount/status?deviceId=ascom:ASCOM.ASIMount.Telescope
  -> {"connected":true,"tracking":false,"slewing":true,"parked":false,
      "rightAscension":0.0,"declination":0.0,"altitude":0.0,"azimuth":0.0,
      "siderealTime":-1.0,"canPark":true,"canSlew":true,"canSync":true, ...}
```

Ground truth, from a standalone PowerShell COM probe against the same driver with Skotiq
disconnected (`C:\src\mountprobe.ps1`):

```
Name: ASI Mount
Connected=true accepted      <- no exception
Connected        = False     <- the driver disagrees
Slewing          = True
AtPark           = False
SiderealTime     = -1
RightAscension/Declination/Altitude/Azimuth = 0
```

So the garbage telemetry is the DRIVER's — Skotiq does not fabricate the `-1`. The defect is
that Skotiq **believed the connect**. `AscomDeviceConnection::connect`
(`native/skotiq_native/ascom/src/windows/connection.rs`) set `Connected = true`, saw no COM
exception, set `self.connected = true` and returned `Ok(())`. It never read the property back —
even though `is_connected()` sits eleven lines below and does exactly that.

**Why this is a P0 for tonight.** `slewing: true` is latched on for ever. Any consumer that waits
for a slew to finish — Slew & Center, meridian flip, the sequencer's own move steps — waits all
night on a mount that does not exist, while the UI insists everything is connected and fine. The
operator's only mistake is picking the wrong entry from a device list that, by ASCOM convention,
advertises installed DRIVERS rather than present HARDWARE.

**Fix written** (`connection.rs`): after setting `Connected = true`, poll `Connected` back for up to
5 s; on failure, set `Connected = false` again so no half-open handle is left behind, and return a
message that names the real possibilities — not powered, not plugged in, or already open in another
application. One function, so it covers every ASCOM device type: mount, camera, focuser, filter
wheel, rotator, dome, switch, safety monitor, cover calibrator, observing conditions.

**Not yet validated on hardware** — this is Windows-only code that cannot compile on the Linux
workstation. It must be rebuilt on the laptop and re-tested against BOTH the phantom ASI mount
(must now fail with the new message) and the five genuinely-attached devices (must still connect).

### Related, still open

`siderealTime: -1.0` reaches the API as a plausible-looking number. Sidereal time has no valid
negative value; a consumer plotting or comparing it gets nonsense rather than a gap. Whether the
transport should carry `null` instead is a contract question, not a driver question.

# Session 2 — live rig, full hardware (2026-08-09 evening)

Real devices connected simultaneously and exercised: **ASI1600MM-Cool** camera, **EAF** focuser,
**EFW2** filter wheel, **ASICAA** rotator, **Pegasus NYX101** mount (ASCOM). Mount parked, daylight.

## What works, verified on hardware

* **Mount telemetry is real and sane.** NYX101 via `ascom:ASCOM.PegasusAstroNYX101.Telescope`:
  parked `true`, slewing `false`, RA 20.0236 h, Dec +87.156°, Alt 39.950°, Az 3.710°, sidereal time
  14.1014 h, side of pier west, plus a per-field `availability` map that honestly marks
  `at_home: unsupported`. This is the contrast case that makes L4 diagnosable.
* **Cooling ramps correctly.** Setpoint 0 °C accepted; sensor 26.7 → 26.0 → 24.5 °C over 36 s with
  cooler power 2% → 8% → 16%.
* **Filter wheel physically moves.** Slot 0 → 1, reported name `1` → `2`, `isMoving` false after.
* **A real 2 s exposure completes** and reports 4656×3520 — the ASI1600MM's true sensor geometry.
* **The oversized-image guard is honest.** `/api/camera/last-image` refuses a 65 MB frame with
  `legacy_image_too_large`, giving `width`, `height`, `displayBytes`, `maxLegacyDisplayBytes` and
  the endpoint to use instead. No truncation, no silent downscale.
* **`filter-wheel/set-by-name` with a nonexistent filter is exemplary.** Asking for `Ha` on a wheel
  reporting `1..8` returns `HTTP 400`, names the filter and the device, lists the available filters
  in both `expected` and `message`, and **does not move the wheel**. This is the opposite of the
  cry-wolf pattern and is worth preserving as the reference shape for the rest of the API.

## L5 — the same mount appears three times, and one of the three cannot connect *(open)*

`GET /api/devices?deviceType=mount` lists the NYX101 as **three separate devices**:

| driverType | id |
|---|---|
| ascom | `ascom:ASCOM.PegasusAstroNYX101.Telescope` |
| alpaca | `alpaca:http://192.168.1.33:80:telescope:0` |
| native | `native:onstep:COM4:115200` |

Nothing tells the operator these are one physical mount. Two of them work; the **native OnStep path
fails**:

```
POST /api/devices/connect {"deviceId":"native:onstep:COM4:115200","deviceType":"mount"}
  -> "Operation timeout: LX200 command response timed out"   (reproduced twice)
```

Discovery itself had already talked to that port successfully — the app's own log line reads
`Found OnStep mount on COM4 at 115200 baud: Pegasus NYX-101#`. So identification over COM4 works and
connection over COM4 does not. A COM4 handle leak in the discovery path was recorded on this same
rig on 2026-06-17, which makes a leaked handle the leading hypothesis, but it is **not yet proven**:
the decisive experiment is a fresh app start with a native connect attempted BEFORE any discovery
runs. Not run yet.

Risk for tonight is low (ASCOM works and is the configured path) but the three-way duplication is a
real trap: connecting two entries for one mount would have two drivers fighting over one serial
port.

## Good — a pre-flight guard that fails closed correctly

First start attempt was refused:

That is exactly right: it names the consequence, not just the missing field. It is also proof the

## L6 — a run starts with NO equipment profile and hangs in "recovering" for ever *(P0 for tonight)*

`GET /api/profiles` → `{"profiles":[]}`. There is no equipment profile on this appliance and no
camera assigned to one. The sequencer started anyway:

```
POST /api/sequencer/start -> {"status":"started"}
GET  /api/sequencer/status ->
  {"state":"recovering","currentNodeId":"e1","currentNodeName":"Sub e1",
   "progress":0.0,"message":"Recovering: Device disconnected"}
```

…and stayed in `recovering / Device disconnected` at `progress 0.0` for the entire observation
window, retrying silently. **No frames were written.**

Meanwhile the device manager disagreed with the executor. Queried during the hang:

```
GET /api/devices/connected -> camera ascom:ASCOM.ASICamera2.Camera,
                              rotator ascom:ASCOM.ASICAA.Rotator,
                              filterWheel ascom:ASCOM.EFW2.FilterWheel, ...
```

So the camera the executor calls "disconnected" is connected, live, and had taken a real 4656×3520
frame minutes earlier. The leading hypothesis is that the executor resolves hardware through the
**profile assignment** rather than the session's connected devices, and an empty profile reads as a
disconnected device — the same shape recorded on 2026-08-05 as "Discovery Connect without Assign
leaves `profile.cameraId` empty". **Not yet proven**; proving it means assigning a profile and
re-running, which is the next test.

Why this is a tonight problem regardless of root cause: the failure is **silent and unbounded**.
The pre-flight layer that correctly refuses a missing save path has no equivalent check for "no
profile / no camera assigned", so the run begins, reports a healthy `started`, and then loops in
recovery until someone notices. On an unattended night that is the whole session lost with no
error surfaced.

## L7 — Stop reports failure after successfully stopping *(P0-adjacent; cry-wolf, opposite polarity)*

> **2026-08-14 (release-pass campaign)**: the whole stop-as-failure family was reworked —
> a `sequenceStopped` notification category, per-producer reclassification (the raw
> `Error` carrying "Sequence cancelled" now classifies as stopped), Session Report titles
> "Stopped (resumable)" with no Errors section, and the toast/banner/rollup surfaces all
> tell the stopped story (Waves D→G, see reports/release-pass/). The HEADLESS API timeout
> path quoted below is a separate producer and was NOT specifically re-verified; on-rig
> validation of the whole family is owed with the next live-rig session.

```
POST /api/sequencer/stop ->
  {"error":"internal_error",
   "message":"TimeoutException after 0:00:30.000000: The native executor accepted the stop command
              but never reported a terminal state within 30s. The hardware was NOT confirmed
              stopped, so nothing has been torn down."}

GET /api/sequencer/status -> {"state":"failed","message":"Cancelled: Preflight"}
```

The run **did** reach a terminal state — the stop worked. The API waited 30 s, gave up, and told the
operator the hardware was *not* confirmed stopped and nothing had been torn down. At 2am that
sentence means "your mount may still be slewing"; it is false, and it is the kind of false alarm
that makes an operator intervene destructively.

A second `stop` against the already-terminal run **also blocks for 30 s** and returns the same
message, rather than returning immediately for a run that is already finished.

The wording itself is admirable — it refuses to claim a teardown it cannot verify. The defect is
that the terminal state arrived and the waiter did not see it.

## L8 — the Dart wire-validation test fixtures do not match the Rust parser

Getting a sequence to load took four rejections, each naming a field the Dart test fixture in
`apps/desktop/test/headless_api/sequencer_wire_validation_test.dart` does not supply or spells
differently:

| Rust demands | fixture has |
|---|---|
| `TargetHeaderConfig.priority` (required) | absent |
| `ExposureConfig.duration_secs` | `duration` |
| `Binning` as a bare enum string (`"One"`) | `{"x":1,"y":1}` (my guess, also wrong) |
| `SequenceDefinition.id` and `name` | absent |

`sequence_wire_validation.dart`'s own doc comment says the point of validating the wire artifact is

correct — but nothing proves it, because no test feeds it a string the Rust side would accept.

## L9 — a profile cannot be created through the headless API, because the error says nothing *(open)*

`POST /api/profiles` with a body carrying `name`, all five real device ids, focal length, aperture,
binning and cooling flags returns:

```
{"error":"Malformed profile payload","code":"invalid_request",
 "field":"profile","expected":"equipment_profile","message":"Malformed profile payload"}
```

No field name, no expected shape, no hint. `profile_handlers.dart:86-92` is the cause:

```dart
try {
  profile = EquipmentProfile.fromJson(profileJson);
} on Object {
  throw BadRequestError(field: 'profile', expected: 'equipment_profile',
                        message: 'Malformed profile payload');
}
```

The intent is good and the comment says so — *"a malformed shape becomes a structured 400 instead of
letting a TypeError/FormatException collapse into an opaque 500"*. But `on Object` swallows the
exception object entirely, and that exception is the only thing that knows **which** field was wrong.
The caller is left to reverse-engineer `EquipmentProfile.fromJson` from source, which is exactly what
I had to start doing.

Compare `filter-wheel/set-by-name`, which for a bad filter returns the device, the requested value,
and the full list of valid ones. Same API, same release. That is the standard this should meet:
include the underlying error's message (it is a local type error, not sensitive), or validate
field-by-field.

Consequence for tonight: **there is no working path to create an equipment profile remotely.** If
L6's root cause is the empty profile, then a headless-only operator cannot fix L6 either.

### Checked: this is not the known profile-store schism

An earlier campaign recorded a schism where the GUI's SQLite store and the remote `/api/profiles`
store were different databases. Not the cause here: the only databases on the laptop are the
scratch ones this session created (`C:\src\rigdata\skotiq.db`, 987 KB, and `pairing.db`).
Nothing exists under `%APPDATA%\com.example\skotiq_desktop` or `%LOCALAPPDATA%`. The machine was
reimaged, so this build's GUI has never run here and there are genuinely zero profiles. `L6` is a
real "started with no profile at all", not a store mismatch.

## L10 — the ZWO CAA rotator is a SECOND phantom, and it silently swallowed a move *(confirms L4; P0 for tonight)*

The earlier PnP scan found only the two cameras — no CAA, EAF or EFW by name — so the rotator was
suspect. Skotiq nonetheless:

```
POST /api/devices/connect  {"deviceId":"ascom:ASCOM.ASICAA.Rotator","deviceType":"rotator"}
  -> {"status":"connected"}
GET  /api/rotator/status   -> {"position":0.0}
POST /api/rotator/move-to  {"angle":30.0}
  -> {"commandId":"708a29ef-...","status":"moving"}
```

`status: moving`. Position then read **0.0 at t+12 s, t+22 s, t+32 s and t+42 s.** Nothing moved,
nothing errored, and the app never stopped claiming it was moving.

Independent COM probe of all three ZWO auxiliaries — the control group that makes this conclusive:

| driver | `Connected` reads back | `Name` | hardware attached |
|---|---|---|---|
| `ASCOM.ASICAA.Rotator` | **False** | ZWO CAA | **no — phantom** |
| `ASCOM.EAF.Focuser` | True | ZWO Focuser | yes |
| `ASCOM.EFW2.FilterWheel` | True | ZWO FilterWheel | yes |

Same rig, same session, same vendor's driver family: the read-back cleanly separates the two real
devices from the phantom, and it is the exact check `AscomDeviceConnection::connect` was missing.
That is now two independent phantoms (ASI Mount, ZWO CAA) caught by one test on one afternoon.

**Why this is worse than the mount case.** A phantom mount at least announces itself through
`slewing: true` forever. A phantom rotator reports a plausible `position: 0.0`, accepts every move
with `status: moving`, and stays silent. A sequence that rotates to frame a target would run all
night at the wrong angle with every frame quietly mis-rotated and no error anywhere. There is no
symptom until the data is reviewed.

This raises L4 from "the fix is written" to "the fix is required before tonight", and it gives the
fix a ready-made acceptance test: after rebuilding, `ASCOM.ASICAA.Rotator` must FAIL to connect with
the new message, while `ASCOM.EAF.Focuser` and `ASCOM.EFW2.FilterWheel` must still connect.

## API ergonomics — four field names guessed wrong in a row

Working the device endpoints by hand, every one of these was rejected before the right spelling was
found: `/api/camera/expose` wants `exposureTime` (not `exposureSeconds`), `/api/focuser/move-relative`
wants `delta` (not `steps`), `/api/rotator/move-to` wants `angle` (not `position` — even though
`/api/rotator/status` *returns* `position`), and `/api/rotator/move-absolute` does not exist at all.
Each rejection was a clean, correct 400 naming the missing field, which is why this is an ergonomics
note rather than a defect — but `status` returning `position` while `move-to` demands `angle` is a
genuine inconsistency inside one device's own endpoint pair.

## L11 — one failed run wedges the camera for the rest of the night *(P0 for tonight)*

After the L6 run failed and was stopped, **every exposure through Skotiq timed out**, while the
camera itself stayed perfectly healthy. Sequence of measurements, all on the live ASI1600MM-Cool:

```
1. Before the run:  POST /api/camera/expose 2s  -> complete, 4656x3520 frame
2. Sequencer run enters "recovering", is stopped (L6, L7)
3. Autofocus:  "Autofocus exposure failed: Exposure ... did not complete within 62.0s timeout
                (2.0s requested exposure plus safety margin);
                CRITICAL: failed to restore original focuser position 22850: halt failed:
                Halt failed: Operation timeout: Focuser halt timed out after 10s"
4. Plain expose 2s        -> same 62 s timeout
5. GET /api/camera/cooling -> {"coolerOn":true,"targetTemp":0.0,"sensorTemp":0.1,"coolerPower":43.0}
                              (telemetry perfectly responsive; the cooler had reached its setpoint)
6. POST /api/camera/abort  -> {"status":"aborted","wasRunning":false,
                               "message":"No exposure was in progress ...; nothing to abort."}
7. Plain expose 2s        -> STILL times out
```

Ground truth, Skotiq disconnected, independent COM client:

```
Connected reads back = True
CameraState = cameraIdle
ImageReady after 2.9s = True
```

**The camera and driver are fine.** The wedge is in Skotiq's own per-connection camera state.
Confirmed by the cure: `POST /api/devices/disconnect` then `/connect`, and the very next exposure
returned `{"status":"complete"}`.

Why this is the worst finding of the session for an unattended night:

* **It is silent in exactly the way that matters.** The dashboard keeps showing a cooled, connected,
  healthy camera — `coolerOn`, setpoint reached, 43% power — while nothing can be captured.
* **`abort` actively misleads.** It reports there is nothing to abort, which is true of the app's
  own bookkeeping and false about the situation, so the one recovery an operator would reach for
  reports success and changes nothing.
* **Nothing self-heals.** The app never reconnects the camera on repeated exposure timeouts, even
  though disconnect/reconnect is a complete and instant cure that it is perfectly capable of
  performing.
* **One bad run poisons the night.** The trigger was a run that failed for an unrelated reason (L6).

### Second defect inside the same failure: autofocus abandons the focuser

The autofocus error is worth reading twice:

> `CRITICAL: failed to restore original focuser position 22850: halt failed: Halt failed:
> Operation timeout: Focuser halt timed out after 10s`

Autofocus moved the focuser, could not expose, tried to put it back, and **failed** — then failed
again trying to halt it. The focuser is left at an unknown position. The app knows this and says so
in capitals, which is genuinely good reporting, but there is no recovery: no retry of the restore,
no re-home, and the run would carry on out of focus. On an unattended night the remaining hours are
captured at whatever focus position the failure happened to leave behind.

The 10 s halt timeout is also worth questioning against a real EAF, which is not a fast device.

## L12 — the safety subsystem's first answer is "unsafe", and it can auto-park *(observed once; needs a restart to re-prove)*

Two consecutive `GET /api/safety/status` calls, seconds apart, no configuration touched in between:

| field | first call | second call |
|---|---|---|
| `isSafe` | **false** | true |
| `safetyStatus` | **unsafe** | safe |
| `hardwareWeatherSafe` / `safetyMonitorSafe` / `apiWeatherSafe` | false / false / false | true / true / true |
| `hardwareWeatherReading` / `safetyMonitorReading` | **unknown** | absent |
| `monitoringEnabled` | **true** | false |

Then ten consecutive polls at 3 s intervals: `isSafe=True` every time. So this is not ongoing
flapping — it is the **first evaluation** after the subsystem comes up, before settings load, where
`monitoringEnabled` is still true and every reading is `unknown` rather than `absent`. Fail-closed
turns "unknown" into "unsafe", correctly, on data that has not arrived yet.

**Observed once.** I did not restart the appliance to reproduce, because a restart would take the
rig offline while other work was using it. Re-proving it needs a cold start with a poll running from
the first second — that test should be run before tonight.

Why it matters tonight, from this rig's own settings
(`GET /api/safety/settings`): `failMode: fail_closed`, **`autoParkOnUnsafe: true`**,
`autoStopOnUnsafe: false`, `warningDelaySeconds: 60`, `requiredSafeDurationSeconds: 300`,
`enabledMonitors: []`.

So a transient "unsafe" is wired to **park the mount**. The 60 s warning delay is the thing standing
between a first-read transient and an automatic park, and whether it covers this window is exactly
what the restart test would establish. Note also `enabledMonitors: []` with `fail_closed` — the
configuration this rig will actually run tonight has no monitors at all, which is the same shape as
the 6.0.0 blocker where fail-closed weather safety aborted every run on a rig with no weather sensor.

The steady-state wording is honest and good: *"Weather safety is off — conditions are not being
checked"*, with `failModeWarning: "No weather data sources available"`. The problem is only the
first answer, and that it is wired to an actuator.

## L13 — every ASCOM *write* discards the driver's explanation; every *read* keeps it *(open, confined, high value)*

Enabling tracking on the parked NYX101 — which the mount correctly refused — produced:

```
POST /api/mount/tracking {"enabled":true}
 -> "Failed to set ASCOM mount ... tracking=true:
     SDK error: Failed to set property Tracking: Exception occurred. (0x80020009)"
```

The behaviour is right: the mount stayed `parked=true, tracking=false, slewing=false`. The message
is a bare HRESULT. ASCOM drivers put a human sentence in the `EXCEPINFO` for exactly this case —
something on the order of *"Cannot set Tracking while the mount is parked"* — and it never reaches
the operator.

Root cause, and it is a one-line asymmetry in `connection.rs`:

* **Property reads** pass a real `EXCEPINFO` and decode it: `excepinfo_to_string` is called at lines
  876, 918, 956, 994 and 1036.
* **Property writes** pass `None`: `invoke_with_retry(dispid, DISPATCH_PROPERTYPUT, &params, None, None)`
  at lines **708, 752 and 795**. The description is never even requested, so nothing downstream can
  recover it.

Consequence: `0x80020009` on *any* write is unexplainable by construction. That covers connect,
tracking, gain, offset, cooling setpoint and filter position — and a previous live-rig session on
this same hardware recorded exactly this pain as "gain/offset + FW-move fault 0x80020009". Every one
of those investigations was chasing a message the driver had already written and the app had thrown
away.

Fix is confined: pass an `EXCEPINFO` from the three `DISPATCH_PROPERTYPUT` sites and feed it through
the same `excepinfo_to_string` path the getters already use. The retry loop needs care — `EXCEPINFO`
carries `BSTR`s that must be freed between attempts — which is presumably why the setters were
written this way.

This also explains why L4's phantom-device message had to be written from first principles rather
than surfaced from the driver: on the connect path there is no description to surface.

## L16 — the pre-flight layer is good, and its gaps are exactly the P0s *(this is the fix for L6 and L14)*

Three start attempts, three different pre-flight outcomes, and the pattern is unmistakable:

| sequence contains | pre-flight verdict |
|---|---|
| exposures, no save path configured | **BLOCKED** — *"This sequence captures frames but no image save path is configured. Set the sequencer save path before starting — every frame would otherwise be captured and discarded."* |
| a CenterTarget step, no plate solver installed | **BLOCKED** — *"This sequence centers on a target but no plate solver (ASTAP or solve-field) was found on this system. Install and configure a plate solver before running — centering would fail on every target otherwise."* |
| an exposure on filter position 0, wheel not visible to the executor | **ALLOWED TO START**, then failed mid-run (L14) |
| exposures with no equipment profile at all | **ALLOWED TO START**, then 90 minutes of silent recovery (L6) |

Both existing guards are excellent and share a shape worth copying verbatim: they name the missing
thing, name the consequence in the operator's terms, and refuse before anything moves. Neither says
merely "invalid configuration".

So L6 and L14 are not a missing capability — they are **two missing entries in a guard list that
already exists and already works**. The sequence declares which devices it needs (a filter index
implies a wheel, an exposure implies a camera, a slew implies a mount); pre-flight already walks the
tree for save paths and centering. The same walk should refuse to start when a required device is
not resolvable by the executor, in the same voice:

> *"This sequence changes filters but no filter wheel is available to the sequencer. Assign one to
> the active equipment profile before running — every exposure that requests a filter would fail."*

That is a far smaller change than fixing the executor/device-manager split (L14), and it converts
the two worst unattended failure modes — a 90-minute silent retry and a bare "Failed" — into a
refusal the operator reads before going to bed. **Both should be done: the guard tonight, the split
properly afterwards.**

## L18 — the ASCOM slot to physical camera binding is not stable *(P1)*

With two ZWO cameras attached, `ASCOM.ASICamera2.Camera` was the ASI1600MM-Cool. With one attached,
the same ProgID is the ASI178MM — and so is `ASCOM.ASICamera2_2.Camera`. The ProgID identifies a
*driver slot*, not a camera.

Skotiq treats the ProgID as the device identity (`deviceId: ascom:ASCOM.ASICamera2.Camera`),
reads capabilities once at connect, and shows a name derived from the ProgID rather than the
driver's `Name` (L2). So all three of the things that would reveal a swap are absent: the id does
not change, the displayed name does not change, and the cached capabilities do not change.

For tonight: if a camera browns out and re-enumerates, the run can continue against the wrong sensor
with the wrong pixel scale, the wrong frame size, and a cooler that does not exist. Reading `Name`
on connect (L2) and re-reading capabilities after any reconnect would both close it.

## L19 — turning the cooler OFF sends a fabricated -10 °C setpoint, and fails

```
POST /api/camera/cooling {"deviceId":"...","enabled":false}     <- no targetTemp sent
  -> "Failed to set ASCOM camera ... cooler (enabled=false, target=-10C):
      SDK error: Failed to set cooler: Failed to set property SetCCDTemperature..."
```

`camera_handlers.dart` correctly forwards `targetTemp: null`. The `-10` is applied two layers down at
`device_manager/ops/camera.rs:2251` and `:2327` — `target_temp.unwrap_or(-10.0)` — and the module
header documents it as "the historical Skotiq default target when the caller does not specify".

A default target is defensible when *enabling* cooling. Applying it while *disabling* is not: no
setpoint is needed to turn a cooler off, and here writing `SetCCDTemperature` is precisely what threw
(the 178MM has no TEC, so `CanSetCCDTemperature` is False). The result is that **the cooler cannot be
turned off at all** on a camera that reports no cooling capability — the request fails as a whole.

End-of-night warm-up is exactly when this is called. It should skip the setpoint write when
`enabled == false`, and skip it when the camera reports `CanSetCCDTemperature == false`.

Genuinely good: real site coordinates, focuser position **and** temperature, sexagesimal and decimal

**Missing, and it matters:**

* **No `INSTRUME`, `TELESCOP` or `FOCALLEN`.** Nothing in the file says which camera or scope took

### Resolution *(2026-08-09)* — one code defect, one configuration gap

Both reproduced against the Linux simulator build before anything was changed; a camera-only run
with no equipment profile wrote a header of exactly the shape above.

**`OBJCTALT`/`AIRMASS` — code defect, fixed.** Not the `altitude: None` on file in
`simulator-fidelity-backlog.md` S5 (already fixed); the live gate is in `instructions.rs`, which
derives alt/az only inside `if let Some(mount_id)`. No mount, no altitude — even though `RA`/`DEC`
were written from the target and altitude is pure geometry from that same pointing plus the site and
the timestamp, all three already in the frame context. Now derived from
`FrameContext::recorded_altitude_deg`, so the altitude and the pointing cards cannot describe
different directions. Re-run after the fix: `OBJCTALT 39.371`, `AIRMASS 1.5736`.

**`INSTRUME` — code defect, fixed.** It was built only from the observer profile, which is a
cross-product of app settings and the ACTIVE EQUIPMENT PROFILE. This rig has no profile, so the
keyword was absent although the camera was connected and named. It now falls back to the driver's
own answer for the connected camera (`DeviceOps::camera_get_model`). A profile that names a camera
still wins.

Caveat worth stating plainly: on this rig the fallback yields the app's current generic label
(`ASICamera2 Camera`), not `ZWO ASI1600MM-Cool`, because of **L2** above. So `INSTRUME` will be
present but will not by itself distinguish the two ZWO cameras until L2 is fixed — at which point it
improves with no further change here. The fallback prefers `display_name`, which carries the serial
when the driver reports one, precisely so it can tell two identical bodies apart.

**`TELESCOP`/`FOCALLEN` — not a code defect.** The wiring is sound and was verified end to end:
`POST /api/sequencer/update-observer-profile` with a telescope name and focal length produced
`FOCALLEN`, `APTDIA`, `TELESCOP`, `INSTRUME` and `OBSERVER` on the very next frame. They are absent
on the rig because no equipment profile exists there (finding **L6**), and no driver can report what
scope the camera is bolted to. **Action for the owner, no rebuild required:** create an equipment
profile, or push one over the API before tonight's run — the values are the operator's to state.

## L24 — frame numbering is per-node, so sibling nodes collide *(moderate)*

Two single-frame `TakeExposure` nodes on one target produced `Polaris_1_0001.fits` and

### L29 root cause — the headless start path re-implements a subset of the Dart executor

`sequencer_handlers.dart` `handleSequencerStart` has two branches:

```dart
final hasInEditorSequence = container.read(currentSequenceProvider) != null;
if (hasInEditorSequence) {
  final executor = container.read(sequenceExecutorProvider);
  await executor.start();                       // <- the full Dart lifecycle
} else {
  // headless load -> start
  await backend.sequencerSetSimulationMode(false);
  ...
  await _wireConnectedDevicesIntoNativeExecutor(backend);
  await backend.sequencerStart();                // <- straight to native
}
```

The Dart branch's `executor.start()` reaches `_startNativeExecution`, which does two host-side
things the bare branch does not. The **first is the one that actually writes the rows**, and my
initial reading of this finding had it wrong — it is worth stating the correction plainly, because
the wrong version would have produced a fix that did not work:

* `runtime_config_operations.dart:161` subscribes `_handleSequencerEvent` to `backend.eventStream`.
  That listener is what turns a native frame event into a `captured_images` row, advances the
  session counters, feeds progress and the run vitals, and drives auto-grading. **Nothing else
  writes those rows.** The headless branch never subscribed, so on the appliance no one was
  listening when the frames came back.
* `sequence_executor.dart:769` `_startSessionRow(sequence)` opens the `imaging_sessions` row. The
  frame insert treats `session_id` as nullable (`event_operations.dart:662-665` deliberately writes
  NULL when no session is open), so this is not what suppressed registration — but without it the
  rows that *do* land are unattributed and the session counters never move. A night as a pile of
  orphan rows is barely better than no rows.

That also explains the one exception exactly. `resumeFromCheckpoint` (`sequence_executor.dart:2194`)
is the **only other place in the codebase** that installs the same subscription, and `ResumeTest` is
the only run that went through it.

An earlier fix had already tripped over this same fact without naming it as the cause: the long
comment at `sequence_executor.dart:1248-1258` documents that "the headless `POST
/api/sequencer/load` -> `/api/sequencer/start` path starts the sequence on the NATIVE executor
without ever calling `start`, so this executor never installs `_nativeEventSubscription` and
`_onTerminalEvent` can never fire" — and worked around the symptom (a Stop that waited 30 s for an
event that could not arrive) rather than the missing subscription.

**This is the same seam that produced L22.** The headless path re-implements a subset of what the
Dart executor does at start, and every omitted step is a separate silent failure:

| step the Dart executor performs at start | headless path |
|---|---|
| wire connected devices into the native executor | **fixed today** (L22) |
| subscribe to the native event stream | **fixed today** — the registration half of L29 |
| open the `imaging_sessions` row | **fixed today** — the attribution half of L29 |
| `startRun` + persist the sequence snapshot | **still missing** — no run-history diff |
| `_bindCatalogTargets(sequence)` | **still missing** — unverified consequences |

The durable fix is not another patch to the `else` branch; it is to make the headless path share one
start routine with the editor path, so a step added for one is present in both. Until then, every
future addition to `executor.start()` silently skips the appliance — which is the configuration that
runs unattended all night with nobody watching.

### L29 fix as landed

`SequenceExecutor.attachHostListenersForNativeRun()` (public, idempotent, safe to call before every
native start — a previous run's teardown cancels the subscription, so run two would otherwise be as
blind as run one) plus `_openSessionRowForNativeRun`, both called from the bare branch before
`sequencerStart()`. The session summary comes from a `_WireSequenceSummary` parsed at
`POST /api/sequencer/load`, because the native executor exposes no way to ask it back for the
sequence name or its targets.

Two details that are not obvious and are pinned by tests:

* **Ordering.** The session row must exist before the first frame event, or that frame is stamped
  `session_id` NULL — the row is opened before the listener is attached and both before the start.
* **The second run of the night.** `SessionService.startSession` refuses to open a session while one
  is active, so a stale row from the previous target would have filed the next target's frames under
  the wrong night. The handler closes an open session first — but only when the native executor
  reports a non-running state, since a busy executor refuses the start with a 409 and ending a live
  run's session on the way to that refusal would corrupt the run in progress.

Tests: `apps/desktop/test/headless_api/sequencer_start_session_row_test.dart` (8 cases). 7 of the 8
fail when the two calls are removed from the start path, including the loop-multiplier denominator
(expected 10, got 0) and the subscription assertion.

## L30 — the disk the app writes to is not the disk it monitors *(P1 for an overnight run)*

```
POST /api/sequencer/save-path {"path":"C:\\src\\rigframes"} -> {"status":"ok","path":"C:\\src\\rigframes"}
   ... 30 FITS subsequently written there ...
GET  /api/system/disk-space -> {"configured": false}
```

Two different settings, no link between them:

* `handleSequencerSetSavePath` validates the directory and then calls
  `backend.sequencerSetSavePath(requested)` — the **native executor's** save path. It never writes
  `appSettings.imageOutputPath`.
* `handleDiskSpace` reads `settings.imageOutputPath`, finds it empty, and returns
  `{"configured": false}` — which the handler's own comment correctly calls "a valid state, not an
  error".

Each is right on its own terms, and together they mean the free-space guard watches a volume the
frames are not going to. On this appliance it is inert: 30 frames written, disk monitoring reporting
"not configured". If both were set but to different volumes it would be worse than inert — it would
report healthy space on the wrong disk while the real one filled.

An overnight run is precisely when this matters. A 100-frame night from the ASI1600 is 3.3 GB; from
a modern full-frame sensor, several times that.

**Credit where it is due, because I had this wrong.** I earlier recorded that pre-flight validates
the save path's *presence* but not its *writability*. It does validate writability, properly:
`handleSequencerSetSavePath` creates the directory, writes a `.skotiq-write-probe-<ts>` file,
deletes it, and on failure returns *"Save path ... is not usable: <reason>. Choose a directory this
host can write to."* That is a real check with a real error. The gap is only that the checked path
and the monitored path are different settings.

### L30 fix as landed

`handleSequencerSetSavePath` now also calls `setImageOutputPath(requested)` after the native call
succeeds, so the one endpoint a headless-only operator has for choosing where frames go points both
the executor and the free-space guard at the same directory. Non-fatal if the settings write fails —
the frames go where the caller asked either way, and refusing a valid save path over a monitoring

### L31 — two different events one letter apart *(minor, but a real trap)*

```
{"category":"sequencer","eventType":"ExposureCompleted","data":{"frame":1,"total":3,"duration_secs":1.0}}
{"category":"imaging",  "eventType":"ExposureComplete", "data":{"success":true}}
```

Not a duplicate emission — two different subsystems reporting different things. But a client author
filtering on `ExposureComplete` silently receives the imaging layer's bare `{"success":true}` and
never sees the sequencer's frame counter, or vice versa. The difference is one character and is
invisible when scanning a log. The `category` field distinguishes them, so this is workable rather
than broken; the names should still say what each means.

## L32 — a wrong-verb request is answered by a parameterised route, not a 405 *(moderate; costs client authors real time)*

```
GET /api/calibration/darks/find-match?...  -> 400 {"error":"Path segment is not a valid integer",
                                                   "field":"id","expected":"integer"}
GET /api/calibration/darks/clear           -> 400  (identical error)
```

Neither path takes an `id`. `find-match` and `clear` are registered as **POST**
(`calibration_routes.dart:52` and `:83`), and the literal routes are correctly declared *before* the
parameterised `GET /api/calibration/darks/<id>` at `:92` — so route ordering is fine. What happens is
that a GET finds no literal GET route, falls through to the `<id>` route, and that handler dutifully
tries to parse `find-match` as an integer.

The result is an error that names a field the caller never sent, about a value they never supplied,
for a path that exists. A `405 Method Not Allowed` naming the accepted verb would have taken seconds
instead of a detour into the route table.

Recorded as a finding rather than as my mistake — though it was also my mistake, and that is the
point: I sent the wrong verb, and the app's answer actively pointed away from the cause. With
`/api/calibration/darks/<id>` and `<id>/download` registered alongside eleven literal sibling paths,
every one of those siblings has the same trap for anyone who guesses GET.

With the correct verb the endpoint behaves properly:
`POST /api/calibration/darks/find-match` → `{"error":"exposureDuration is required","field":"exposureDuration","expected":"number"}` —
a clean, named-field 400.

### L32 fix as landed — fixed for the whole API, not for `find-match`

The headless server registers every route through one declarative table
(`routes/headless_route.dart` `registerRoutes`), which makes the table the single source of truth for
what exists. `withMethodNotAllowedFallbacks` now expands that table: for every **literal** path, each
verb the path does not implement gets a synthesized `405` carrying an RFC 9110 `Allow` header and a
body naming the verbs that do work. A path added tomorrow gets the correct answer without anyone
remembering to ask for it.

Three deliberate limits:

* **Parameterised paths are skipped.** `<id>` matches whatever the caller sent, so "this path exists
  but not with that verb" is not a claim the expander can make about them.
* **`HEAD` and `OPTIONS` are never synthesized.** HEAD is a legitimate probe of a GET route and
  OPTIONS is CORS preflight; answering either 405 would break working clients.
* **Ordering is load-bearing.** Each stub is inserted immediately after the LAST real registration of
  its path — behind the handlers that implement it, ahead of any parameterised route declared later.
  That is the same ordering rule the literal routes themselves already depend on, and a test asserts
  it rather than trusting it.

An unregistered path is still a 404: 405 asserts the path exists, and claiming it for a path nobody
registered would be a new lie in place of the old one.

Tests: `apps/desktop/test/headless_api/method_not_allowed_test.dart` (8 cases, including the verbatim
rig request). The whole 947-test headless suite is green with the expansion active, which is the
regression check that matters — every existing route now passes through it.

## L46 — a paused run reports itself as running *(P0 for an unattended night; fixed)*

Found by running the full multi-target rehearsal on the Linux appliance rather than by reading code.
The run stopped dead and the API said it was healthy:

```
02:38:41  log: Trigger fired: HFR Degradation - action: Autofocus
          log: Autofocus failed — HFR baseline reset ...
          log: Execution paused at boundary, waiting for resume...
02:45:22  GET /api/sequencer/status
          -> {"state":"running","currentNodeId":"d1","currentNodeName":"Settle",
              "progress":0.333,"message":"Delay: 2s remaining (0%)"}
```

Seven minutes parked, reported as `running`, with a two-second delay that had lasted seven minutes.
Nobody asked for a pause: an always-armed HFR-degradation trigger force-fired after a filter change,
its autofocus action failed, and `executor/mod.rs` took the documented "pause for operator
intervention" branch. That policy is defensible for an attended run. What is not defensible is that
the operator is never told.

**Not confined to triggers.** The same probe against an explicit operator pause:

```
POST /api/sequencer/pause  -> {"status":"paused"}
GET  /api/sequencer/status -> {"state":"running", ...}
```

So **every** pause was misreported, however it arose.

### Root cause

`SequencerState` — the body of `GET /api/sequencer/status` — is built from the `SequenceProgress`
snapshot (`bridge/src/api/sequencer.rs`, `impl From<SequenceProgress> for SequencerState`), **not**
from the executor's `state` lock. Every pause path wrote the lock and left the snapshot alone:

* the `ExecutorCommand::Pause` arm of the command handler (the operator pause), and
* **eighteen** trigger/safety pause sites in the executor's trigger monitor.

The recovery driver is the one place that got it right — it writes both
(`*recovery_driver_state.write() = Running` **and** `prog.state = Running`), which is exactly the
pattern the other nineteen were missing.

### Fix

Every site that parks the executor now stamps the progress snapshot too, and `Resume` does the
mirror-image update so a resumed run cannot report as paused — swapping one untruth for the other
would have been the classic *relocated defect*.

Verified live on the rebuilt appliance:

```
POST /api/sequencer/pause  -> GET status -> {"state":"paused", ...}
POST /api/sequencer/resume -> GET status -> {"state":"running", ...}
```

776 Rust sequencer tests green.

### The rehearsal that found it, completing cleanly afterwards

Two targets, a nested `Count` loop, two filter changes, a delay node, and a pause/resume in the
middle:

```
planned    2 frames (Target A, Filter 2) + 2x2 frames (Target B, Filter 1) = 6
registered 6      by filter {'Filter 1': 4, 'Filter 2': 2}
session    total=6  ok=6  integration=9.0s (6 x 1.5s)  status=completed
```

The `totalExposures` denominator applied the loop multiplier correctly end to end — the thing the
unit test asserts, now observed against a running appliance.

### Left open, deliberately

The status `message` still reads `"Delay: 2s remaining"` while paused. The state is now truthful,
which is the load-bearing half; the per-site pause reason would have to be threaded through
nineteen call sites, each with its own wording, and inventing one would be guessing. Recorded rather
than half-done.

Also unresolved as a *policy* question, not a defect: an always-armed HFR trigger whose autofocus
fails will park an unattended run until morning. Whether that should instead log-and-continue on a
rig with nobody watching is the owner's call.

## L50 — an interrupted run's checkpoint records zero integration *(P2, fixed)*

Found by aborting a run in the GUI and relaunching: the startup "Recover Sequence?" modal offered to
resume, and the checkpoint behind it read, on disk:

```json
{ "completed_exposures": 3, "completed_integration_secs": 0.0,
  "executor_state": "Paused", "is_active": true,
  "timestamp": "2026-08-10T06:37:41Z" }
```

Three frames of an 8-second exposure node had completed — 24 seconds of sky — and the checkpoint
recorded none of it.

**Cause.** The executor credited integration in one lump from the exposure node's closing progress
event (`final_upd.completed_exposure_secs = Some(total_exposure_time)`), gated on
`result.status == NodeStatus::Success`; per-frame events deliberately carried `None` to avoid
double-counting. So a node that was paused, aborted or failed contributed exactly zero seconds no
matter how much of it had run. This matters most where it hurts most: a real unattended night is one
long exposure node per filter, so a crash at 04:00 after six hours of imaging would have offered a
resume dialog reading "0m integration".

**Fix.** Credit each frame as it lands, on the same monotonic `current > *last` sighting that already
makes `completed_exposures` exactly-once under retries and batched bursts — demonstrably correct,
since the same checkpoint held an accurate `completed_exposures: 3`. The closing one-shot now
contributes only the remainder (`(total - already_credited).max(0.0)`), so a producer with no
per-frame duration — smart exposure is not in `exposure_node_metadata` — still gets its whole burst
counted, and a completed TakeExposure node never adds twice.

**Verified in the running app**, by repeating the measurement that found it:

| | before | after |
|---|---|---|
| paused mid-node, 3 frames × 8s | `completed_integration_secs = 0.0` | **24.0** |
| same run resumed to completion | — | `framesCaptured 10, integrationSecs 80.0` (= 10 × 8, no double count) |

776 `skotiq_sequencer` tests pass.

**Scope correction, established rather than assumed.** `sequence_runs.stats_json` for the *earlier*,
pre-fix interrupted run already read `framesCaptured 5, integrationSecs 40.0`. The Dart-side session
report was therefore never wrong; only the Rust executor's counter — the one feeding the checkpoint
and the resume dialog — was. Worth stating plainly, because the first framing of this finding was
broader than the evidence supported.

**Two related things left open, both observed and neither fixed here.** After a deliberate Stop the
checkpoint still holds `executor_state: "Paused"` and `is_active: true`, so the next launch offers to
resume a run the operator chose to end; and the checkpoint's frame count lags the run (it read 3
while the UI showed 6), so a resume re-shoots frames already on disk. Conservative rather than lossy
— it redoes work instead of skipping it — but both are real and want a decision about when a
terminal state should clear the checkpoint.

**Build trap worth recording:** `flutter build linux --release` does NOT rebuild the Rust. The bundle
kept a stale `libskotiq_bridge.so` and the first verification attempt was measuring the old
binary. Run `cargo build --release -p skotiq_bridge` and copy it into `bundle/lib/` before
believing any native-side result.

**Also withdrawn:** the resume modal appeared to report a status of "Completed" for an interrupted
run. It does not — `Completed` is the *label* of the row whose value is "N frames (Mm integration)".
The accessibility tree flattened label and value into sibling nodes and I assembled them wrongly.

## L51 — WITHDRAWN: the run I thought I stopped was aborted by the dawn trigger *(not a defect)*

Reproduced three times in the GUI: start a run, let it run long enough to write a checkpoint, press
Stop, see the session report, relaunch. The app opens with

> **Recover Sequence?** — A previous sequence was interrupted and can be resumed.

for a run the operator deliberately ended. Pressing Resume there starts slewing. `sequence_runs`
records the run as `stopped`, but the on-disk checkpoint keeps `executor_state: "Running"` and
`is_active: true`, and `can_resume()` is exactly `is_active && state ∈ {Running, Paused} && root`.

**What is established.** Normal completion already handles this: the `NodeStatus::Success | Skipped`
arm calls `mark_completed()`, which is why a finished run opens with "Continue Session" rather than
"Recover Sequence?". The stop path reaches `NodeStatus::Cancelled` — confirmed in the app log,
`execute_children_sequential completed with result: Cancelled` — and that arm never calls it.

**Why the obvious fix is not the fix.** `Cancelled` is also where a weather or dawn abort lands, via
the trigger monitor's `terminate_with`. Those runs *should* stay resumable — being offered the night
back once the sky clears is the point — so clearing on every cancellation would break the case the
banner exists for. The two have to be told apart.

**What was tried and reverted.** An `operator_stopped` flag, set in `LifecycleExt::stop()` beside
`is_cancelled` (not in the `ExecutorCommand::Stop` handler — `stop()` raises `is_cancelled`
synchronously and only then sends the command, so the run can terminate before that command is ever
dequeued; a first attempt that set the flag in the handler failed for exactly that reason), read in
the `Cancelled` arm to call `mark_completed()`. It compiled, all 776 sequencer tests passed, and it
**still did not suppress the banner** on a live stop. Reverted rather than left in the tree, because
a fix that does not work is worse than none — it reads as closed.

**The unexplained part, for whoever picks this up.** After the stop the checkpoint file's mtime is
the stop instant *to the second* (03:42:01 for a stop at 07:42:01Z), yet its contents are still
`Running` / `is_active: true`. So something writes the checkpoint at teardown and preserves the stale
state. It is not the streaming checkpoint task — that `break`s out on `is_cancelled` without
writing. Note also that `mark_completed()` is `if let Ok(Some(..)) = self.load()` and returns
`Ok(())` when the load yields `None`, so it is a **silent no-op** on a missing or unreadable
checkpoint; it cannot distinguish "marked" from "did nothing". That silence is the first thing to
remove — the next attempt should log whether it actually wrote, and dump the file immediately after.

Impact is limited: the prompt requires an explicit click, and the run it offers is genuinely
resumable. It is a false claim about what happened, not a data-loss path.

## L52 — the reason a night ended is never persisted or shown *(P2, not fixed)*

When a trigger ends a run, nothing the operator can reach says which trigger, or that a trigger was
involved at all. Three runs on 2026-08-10 were terminated by `Dawn Approaching` firing
`ParkAndAbort`. What each surface offers afterwards:

| surface | what it says |
|---|---|
| app log (not user-facing) | `WARN Trigger fired: Dawn Approaching (dawn_approaching) - action: ParkAndAbort` |
| `sequence_runs.status` | `stopped` — byte-identical to an operator pressing Stop |
| `stats_json` | `triggerFires: 1` (a count, not a name), `errorMessages: ["Sequence cancelled"]` |
| session report at abort time | "New Sequence - stopped" |
| Analytics → History → run detail | statistics, `Integration 0.00h`, "No images captured in this session" |

So an operator who left the rig unattended and comes back to a night that ended at 03:31 with zero
frames is told "stopped" and "Sequence cancelled", and has no way short of reading the raw log to
learn that dawn ended it — or to distinguish that from a weather abort, a hardware fault, or their
own click.

**Impact is demonstrated rather than argued.** This defect misled *me*, with database access and the
source open, into writing up L51 as a real defect and building a fix for it. `sequence_runs` records
a trigger abort and an operator stop identically, so I read the resume prompt as wrong when it was
right. It took grepping the application log to find out. An operator has strictly less information
than I did.

**Where to fix it.** The name is available at the moment of termination — `terminate_with` receives
the fired triggers and a reason string, and already logs both. What is missing is carrying that into
the run record: `RunStats` has `triggerFires` (a count) and `errorMessages`, and the `Cancelled` arm
emits a bare `"Sequence cancelled"`. Attributing it there — "Ended by trigger: Dawn Approaching
(park and abort)" — would reach the session report, the History detail and the database at once,
because all three read that record.

Not fixed here. It is a Rust change on the same teardown path as L50/L51, and this session has
already shown that path is easy to change and hard to verify; recording it fully is worth more than
a third unverified attempt.

**Related, and cheap:** `mark_completed()` returns `Ok(())` when its `load()` yields `None`, so a
no-op is indistinguishable from success. Any work on this path should remove that silence first.

**Update — the fix is cheaper than described above.** The Sequencer's Execution History already
filters on a status vocabulary that distinguishes these cases: its chips are **Aborted**, Stopped,
**Paused-stopped**, **Interrupted**, Running, and `'aborted'` exists as a status string in the
models. But `sequence_runs` in practice only ever holds `completed`, `stopped` and `paused-stopped`
— the three dawn-terminated runs were filed as plain `stopped`, and no run has ever been recorded as
`aborted`.

So the distinction the UI is already built to display is simply never written. Recording a
trigger-initiated termination as `aborted` rather than `stopped` would light up the existing
Execution History filter and separate it from an operator stop, without any new UI. Carrying the
trigger *name* into `errorMessages` alongside it would answer "which trigger" as well. That is a
smaller change than the teardown rework I assumed, and it is the first thing to try.

### L52 fix as landed

Two changes, no new UI:

1. **Native-initiated terminals are filed `aborted` unless the wire names the operator.**
   The `Stopped`/`SequenceStopped` arm in `event_operations.dart` only ever claims a run the
   Dart `stop()` did not command (an explicit stop's finalization swallows the echo), so a
   terminal arriving there came from the native side — a trigger's ParkAndAbort, a watchdog, a
   safety abort. It now reads `sequenceStopEvidenceProvider`: `operatorPress` evidence (the
   remote/headless Stop decision row) still files `stopped`; everything else, including the
   cause-not-recorded case, files `aborted` — the status every history surface already renders
   as "a safety rule or a trigger ended it". The cause sentence (`sequenceStoppedMessage`, e.g.
   "Parked by the Dawn Approaching trigger") is recorded into `warningMessages` — not
   `errorMessages`, because a safety end is not a fault — and it lands inside `_onTerminalEvent`
   *after* the duplicate/echo guards, so a swallowed terminal can never stamp a foreign cause
   onto a run it did not end. `_lastRunEndOrigin` treats `aborted` as `safety`, matching the
   existing autopilot-reconcile contract for uncommanded stops.

2. **`mark_completed()` no longer returns `Ok(())` for a no-op.** A `None` load now returns an
   error ("no checkpoint on disk to mark") and a corrupt checkpoint propagates its load error
   instead of being swallowed — the start.rs caller already logs mark failures loudly, so the
   silence is gone without new plumbing.

Pinned by `sequence_executor_run_lifecycle_test.dart` (a TriggerFired ParkAndAbort → Stopped
finalizes `aborted` with the trigger name in `warningMessages`; an operator decision row keeps
`stopped`) and two new `checkpoint.rs` tests (absent-file and corrupt-file `mark_completed`
both error). Verified: 76/76 sequence-executor Dart tests, 18/18 checkpoint Rust tests.

**Residual:** an *explicit* `stop(origin: 'scheduler')` still files `stopped`/`paused-stopped`
— the runStatus there comes from the retained finalization intent, not the evidence fold.
Whether a scheduler re-plan should read "Aborted" is a product call; the origin is already
recorded for the reconcile.
