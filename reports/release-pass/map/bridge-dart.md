## 0. Orientation — what is generated and what is not

This matters more than usual here, because the two files named in the task brief
(`lib/src/api/imaging.dart` 2495, `lib/src/api/sequencer.dart` 1322) are **both
flutter_rust_bridge output**, not hand-written.

`packages/skotiq_bridge/lib` totals 92,618 lines of Dart. Of that,
**87,131 lines are generated** and 5,487 are hand-written.

Generated (exempt from the oversize rule, but see §1 for the Rust-side split):

* Everything under `lib/src/api/` — all 23 files carry
  `// This file is automatically generated ... @generated by flutter_rust_bridge@ 2.11.1`
  on line 1–2. Verified with `grep -rl "automatically generated" lib/`.
* `lib/src/frb_generated.dart` (27,838), `frb_generated.io.dart` (24,285),
  `frb_generated.web.dart` (4,226).
* `lib/src/event.dart` (1,260), `device.dart` (710), `device_capabilities.dart`
  (1,107), `error.dart`, `state.dart`, `storage.dart`, `lib.dart` — all FRB mirror files.
* All `*.freezed.dart` (`event.freezed.dart` 9,024, `error.freezed.dart` 2,709, …).

Generation contract (`native/skotiq_native/flutter_rust_bridge.yaml`):
`rust_input: crate::api`, `rust_root: bridge/`,
`dart_output: ../../packages/skotiq_bridge/lib/src/`. The mapping is 1:1 —
one Rust module under `bridge/src/api/` produces one Dart file under
`lib/src/api/`. **You cannot split a generated Dart file directly; you split the
Rust module and re-run codegen via `scripts/dev.sh`.**

### 1.3 `lib/src/bridge_stub/sequencer_operations.dart` — 1057 lines — HAND-WRITTEN — risk: medium

**Why it is big.** 38 methods, and **35 of them are the identical 20-line
boilerplate**:

```dart
Future<void> sequencerX(args) async {
  if (!_nativeAvailable) { _nativeBridgeRequired('sequencerX'); }
  try {
    await gen_api.apiSequencerX(args);
    developer.log('[Bridge] …', name: 'NativeBridge', level: 800);
  } catch (e) {
    developer.log('[Bridge] Error …: $e', name: 'NativeBridge', level: 1000);
    rethrow;
  }
}
```

Measured across `bridge_stub/`: 102 `_nativeBridgeRequired(` call sites,
69 `rethrow;`, 133 `developer.log(`. In this file alone: 38 / 38 / 59.

The pattern adds **nothing** over calling `gen_api.apiSequencerX` directly
except (a) a fail-closed guard and (b) a log line — both of which can be
factored into one helper.

**Split plan.** Do the de-boilerplating first, then the file does not need a
split at all (it drops to ~350 lines).

1. Add `lib/src/bridge_stub/native_call.dart` (new `part`):

   ```dart
   part of '../bridge_stub.dart';

   extension _NativeCall on _NativeBridgeImplementation {
     Future<T> _native<T>(String op, Future<T> Function() body, {String? okLog}) async {
       if (!_nativeAvailable) _nativeBridgeRequired(op);
       try {
         final r = await body();
         if (okLog != null) developer.log('[Bridge] $okLog', name: 'NativeBridge', level: 800);
         return r;
       } catch (e) {
         developer.log('[Bridge] Error in $op: $e', name: 'NativeBridge', level: 1000);
         rethrow;
       }
     }
   }
   ```

2. Rewrite each of the 35 pass-throughs as a one-liner:

   ```dart
   Future<void> sequencerSetSavePath({String? path}) => _native(
     'sequencerSetSavePath',
     () => gen_api.apiSequencerSetSavePath(path: path),
     okLog: 'Set sequencer save path: ${path ?? "<none>"}',
   );
   ```

3. **What must NOT be collapsed** (these have real bodies — keep them verbatim):
   * `sequencerSubscribeEvents` (lines 26–49) — idempotence flag `_sequencerEventsSubscribed`.
   * `sequencerStart` (647–666) — calls `sequencerSubscribeEvents()` first, then sets `_sequencerState`.
   * `sequencerPause/Resume/Stop/Reset/ResumeFromCheckpoint` (669–724, 796–813, 1004–1020) — mutate `_sequencerState` / `_loadedSequenceJson`.
   * `sequencerLoadJson` (52–68) — caches `_loadedSequenceJson`.
   * `sequencerGetStatus` (862–889) — computes `calculateSequencerProgressFraction` and maps to `SequencerStatus`.
   * `sequencerGetCheckpointInfo` (932–957) — FRB→local type mapping.
   * `sequencerUpdateDefaultAdaptiveExposure` (578–619) — flattens 3 maps into 6 parallel lists.
   * `sequencerEventStream` (820–832), `getSequencerState`, `isSimulationMode` — no try/catch.

4. Then split what remains into two parts:
   * `bridge_stub/sequencer_control.dart` — lifecycle + state (`subscribe`, `load`, `start/pause/resume/stop/skip/skipToNode/reset`, `getStatus`, `getSequencerState`, `eventStream`, `pluginNodeFinished`, `setSimulationMode`, `performMeridianFlip`).
   * `bridge_stub/sequencer_config.dart` — every `sequencerSet*` / `sequencerUpdate*` / `sequencerClear*` + the checkpoint five.
   * `calculateSequencerProgressFraction` (top-level, lines 3–11) stays in `sequencer_control.dart` — it is public and covered by `test/sequencer_progress_test.dart`.

**Effort:** medium. Behaviour-preserving as long as step 3 is respected. The
error-message text changes from `'Error <verb> …'` to `'Error in <op>'`; grep
first for tests asserting on those strings (`grep -rn "Error starting sequence" packages` → none today).

## 2. Duplication

### 2.1 The `NativeBridge` facade is a third layer over an already-thin wrapper — CANONICAL: the generated `api/*.dart`

**Evidence.** `native_bridge_facade.dart` is 587 lines containing exactly 153
static members, every one of which is a pure one-line delegation
(`static Future<void> sequencerPause() => _nativeBridge.sequencerPause();`,
line 449). The implementation it delegates to is itself, in ~110 of those cases,
a pure `gen_api.apiX(...)` pass-through (see §1.3 and
`storage_and_image_operations.dart:10–233`, where 20 of 21 methods are
`guard; return gen_api.apiX(...)` with no logging at all).

Consumers already bypass it half the time — see the `bridge_api.` vs
`NativeBridge.` table in §0. `image_polar_operations.dart` and
`session_heartbeat_operations.dart` use the generated API exclusively and lose
nothing.

**Canonical survivor:** the generated `api/*.dart` (re-exported via
`lib/src/api_barrel.dart`).

**What merges into it:** for every facade method whose implementation is a pure
pass-through, delete the facade entry *and* the impl method, and change the
`skotiq_core` call site from `NativeBridge.x(...)` to `bridge_api.apiX(...)`.
That is ~110 of 153 members, ≈700 lines across `native_bridge_facade.dart`,
`storage_and_image_operations.dart`, `equipment_operations.dart`, and
`sequencer_operations.dart`.

**What must stay in `NativeBridge`** (these hold Dart-side state or logic the
generated API does not have):
`init`, `isNativeAvailable`, `getNativeVersion`, `nativeLibrary`,
`eventStream` (fallback re-mapping), `discoverDevices` +
`invalidateDiscoveryCache` (the 60 s cache + single-sweep completer),
`connectDevice` / `disconnectDevice` / `isDeviceConnected` /
`getConnectedDevices` (the `_connectedDevices` bookkeeping and Alpaca
fallback), all `phd2*` and `guider*` (the `_phd2Client` fallback and
`_canonicalGuiderDeviceId` normalisation), `sequencerStart/Pause/Resume/Stop/
Reset/LoadJson/GetStatus/GetSequencerState` (`_sequencerState`),
`sequencerSubscribeEvents`, `sequencerGetCheckpointInfo`,
`sequencerUpdateDefaultAdaptiveExposure`, `apiGetImageStats`.

**Effort:** large, but mechanical and highly parallelisable (one call site at a
time). Do it *after* §3.2 removes the dead facade members, which cuts the work
by ~40 entries for free.

### 2.2 A complete second device stack in Dart, only reachable when the native library fails to load — CANONICAL: Rust

Three hand-written Dart client implementations exist solely for the
`!_nativeAvailable` branch:

| Dart | Lines | Rust counterpart | Lines |
|---|---:|---|---:|
| `lib/src/phd2_client.dart` | 970 | `native/skotiq_native/imaging/src/phd2.rs` | 2201 |
| `lib/src/alpaca_client.dart` | 619 | `native/skotiq_native/alpaca/src/{client,discovery}.rs` | 2443 |
| `lib/src/ascom_client.dart` | 508 | `native/skotiq_native/ascom/src/` | 6179 |
| supporting: `utils/retry.dart` (193), `utils/circuit_breaker.dart` (294), `rolling_rms_calculator.dart` (72) | 559 | (Rust has its own retry/backoff) | — |

Gating evidence:
* `guiding_operations.dart:24` — `if (_nativeAvailable) { … gen_api.apiPhd2Connect(…); return; }` before any `_phd2Client` use; the same shape repeats at lines 142, 169, 200, 321, 343, 363, 389, 402, 418, 438, 449, 465, 556, 568.
* `discovery_operations.dart:297` — ASCOM registry discovery is inside `if (!_nativeAvailable && Platform.isWindows)`.
* `discovery_operations.dart:334` — Alpaca UDP + PHD2 subnet scan are inside `if (!_nativeAvailable)`.
* `connection_operations.dart:98/154` — Alpaca is the *only* family that can reach the Dart client with native loaded, and only after a native connect failure.
* `bridge_stub.dart:12–15` (the library docstring) states the policy: *"this bridge will NOT fall back to simulator implementations … Use INDI/ASCOM/Alpaca external simulators for testing instead."*

The doc says fail-closed; the code carries 2,656 lines of a second
implementation that fires when the DLL is missing. Those two facts contradict
each other.

**Canonical survivor:** Rust. **Recommendation:** decide the policy explicitly.
Either (a) delete the Dart fallback stack and let `!_nativeAvailable` fail closed
everywhere — consistent with the stated policy and with
`_nativeBridgeRequired`'s existence — or (b) keep it and write down when it is
supposed to run. Do not ship both with an undocumented split. If (a): delete
`phd2_client.dart`, `alpaca_client.dart`, `utils/retry.dart`,
`utils/circuit_breaker.dart`, `rolling_rms_calculator.dart`, the `!_nativeAvailable`
tails of `guiding_operations.dart`, `_connectAlpacaDevice` /
`_connectAscomDevice`, and the fallback sections of `_runFullDiscoverySweep`;
keep `ascom_client.dart`'s `discoverAscomDrivers` only if the Windows registry
fallback is still wanted. Also delete the four tests that exist only to cover the
fallback (`alpaca_client_test.dart`, `phd2_event_parsing_test.dart`,
`phd2_rpc_test.dart`, `rolling_rms_calculator_test.dart`,
`connection_resilience_test.dart`). **Effort: large.**

### 2.3 Two `apiDiscoverIndiAtAddress` — one Rust, one Dart, and production calls the Rust one

**Merge:** delete `NativeBridge.apiDiscoverIndiAtAddress` (facade line 16–19),
the impl (`discovery_operations.dart:9–90`), `_parseIndiDevices` (93–193), and

**Effort: small.** Highest value-per-line in this report.

### 2.5 `phd2*` and `guider*` are the same eight operations twice

`guiding_operations.dart` defines a matched pair for every guider operation:
`phd2StartGuiding`/`guiderStartGuiding` (164 / 314), `phd2StopGuiding`/`guiderStop`
(199 / 341), `phd2Dither`/`guiderDither` (—/354), `phd2Loop`/`guiderLoop`
(555 / 387), `phd2FindStar`/`guiderFindStar` (—/400),
`phd2SetLockPosition`/`guiderSetLockPosition` (—/411),
`phd2GetLockPosition`/`guiderGetLockPosition` (—/434),
`phd2DeselectStar`/`guiderDeselectStar` (—/447),
`phd2GetStarImage`/`guiderGetStarImage` (567 / 460).

The `guider*` variants are the unified, device-id-parameterised form; each one's
non-native branch is literally
`if (normalizedDeviceId == 'phd2_guider') { await phd2X(...); return; }`
(e.g. lines 330–337, 347–350, 374–383). The `phd2*` variants are the legacy
PHD2-only form. `_canonicalGuiderDeviceId` (`bridge_stub.dart:79`) exists purely
to bridge the two naming schemes.

**Canonical survivor:** `guider*`. **Merge:** the `phd2*` methods become private
helpers of the `guider*` ones (or vanish entirely if §2.2(a) is chosen). Facade
entries `phd2StartGuiding`, `phd2StopGuiding`, `phd2Dither`, `phd2Loop`,
`phd2FindStar`, `phd2SetLockPosition`, `phd2GetLockPosition`,
`phd2DeselectStar`, `phd2GetStarImage` should go once `skotiq_core`'s
`mount_guiding_operations.dart` is switched to the `guider*` forms.
**Effort: medium** (requires touching the core call sites).

### 2.6 PHD2 install-detection duplicated across three platform methods

`discovery_operations.dart:642–773`: `_isPhd2InstalledWindows`,
`_isPhd2InstalledMacOS`, `_isPhd2InstalledLinux` are 130 lines of the same
shape — a path list, then `which`, then `pgrep`/`tasklist`, then a package
manager. The Windows PHD2 path list at 643–648 is byte-identical to the one at
`guiding_operations.dart:53–58`.

**Merge:** one `_isPhd2Installed({required List<String> paths, List<List<String>> probes})`
plus a per-platform const path table; hoist the Windows path list to a single
`const _phd2WindowsPaths`. **Effort: small.** Subsumed by §2.2(a).

## 4. Performance risks

### 4.1 `apiAutoStretchImage` / `apiDebayerImage` / `apiCalibrateImageData` / `apiGenerateFitsThumbnail` are generated **sync** and block the calling isolate — impact: HIGH

**Evidence.** 60 of the generated top-level API functions have non-`Future`
return types, i.e. FRB `sync` mode. The heavy ones:

* `lib/src/api/imaging.dart:456` — `Uint8List apiAutoStretchImage({...})`
* `lib/src/api/imaging.dart:485` — `Uint8List apiDebayerImage({...})`
* `lib/src/api/imaging.dart:501` — `Uint8List apiGenerateFitsThumbnail({...})`
* `lib/src/api/imaging.dart:557` — `Uint16List apiCalibrateImageData({...})`
* `lib/src/api/imaging.dart:445` — `ImageStatsResult apiGetImageStats({...})`
* `lib/src/api/plate_solve.dart:48` — `PlateSolverDetection apiPlatesolveDetect()`

A sync FRB call runs the Rust body on the Dart thread. For a full-frame stretch
or debayer of a 24 MP sensor that is hundreds of milliseconds of jank per call.

Live call sites (cross-package, listed so the implementer can measure):
`skotiq_core/lib/src/providers/auto_stretch_provider.dart:232`,
`skotiq_core/lib/src/services/stacking_engine_seam.dart:190`,
`skotiq_core/lib/src/services/calibration_service.dart:373`,
`skotiq_core/lib/src/services/thumbnail_sidecar_service.dart:48`,
`skotiq_core/lib/src/backend/ffi_backend/session_heartbeat_operations.dart:84`,
`skotiq_core/lib/src/backend/ffi_backend/image_polar_operations.dart:58`,
`skotiq_core/lib/src/backend/ffi_backend/mount_guiding_operations.dart:669`.

`auto_stretch_provider.dart` is the sharpest case: the doc comment at line 221
says *"This is compute-intensive, so it runs in an isolate"*, and the Dart
fallback at line 240 does use `compute(...)` — but the Rust path at line 232 is
a bare synchronous call on whatever isolate the provider runs on.

**Fix (bridge side):** drop `#[frb(sync)]` from these Rust functions so they
generate as `Future` and run on the FRB worker pool. That is a signature change
(callers must `await`), so it is a coordinated bridge+core change. Measure first
with a full-res frame before committing to it.

### 4.2 `rawData.toList()` before the sync stretch — impact: HIGH (cross-package, at our boundary)

`skotiq_core/lib/src/providers/auto_stretch_provider.dart:234` passes
`data: rawData.toList()` where `rawData` is a `Uint16List`. `.toList()` allocates
a fresh `List<int>` and copies element-by-element — for a 24 MP frame that is
24 M boxed-int slots and a full O(n) copy, immediately before the *synchronous*
Rust call of §4.1. The generated signature
(`imaging.dart:456`, `required List<int> data`) is what forces the copy.

**Fix:** change the Rust parameter to `ZeroCopyBuffer<Vec<u16>>` (or accept
`Uint16List` directly) so FRB generates a typed-data parameter and the copy
disappears. Bridge-side change, core-side call-site update.

### 4.3 PHD2 subnet scan opens up to 254 TCP sockets per interface — impact: MEDIUM (fallback path only)

`discovery_operations.dart:542–578` (`_scanSubnetForPhd2`) iterates
`for (int i = 1; i <= 254; i++)`, creating a `Socket.connect` with a 500 ms
timeout for each, in batches of 50. `_getLocalNetworkAddresses`
(`discovery_operations.dart:507–538`) enumerates **every** IPv4 interface and
derives a /24 per address — on a dev box with Docker, a VPN and Wi-Fi that is 3+
subnets, i.e. 750+ connect attempts, ≈8 s of the discovery sweep.

Reached only from `_runFullDiscoverySweep`'s `if (!_nativeAvailable)` branch
(line 334) → `_discoverPhd2Instances` (line 373). Goes away entirely under §2.2(a).

### 4.4 Discovery cache is a full sweep of all 11 device types on any single-type miss — impact: LOW (intentional)

`discovery_operations.dart:207–240`: a request for one `DeviceType` that misses
the 60 s cache runs `_runFullDiscoverySweep()` across `DeviceType.values`. This
is deliberate and documented (lines 203–206: *"A single sweep discovers ALL
device types so that concurrent callers … share one network scan"*), and the
`_discoverySweepInProgress` completer correctly coalesces concurrent callers.
Recorded as understood behaviour, not a defect.

### 4.5 No provider/widget perf risks in this package

`skotiq_bridge` contains no `Widget`, no `ConsumerWidget`, and no Riverpod
provider. `grep -rn "ref.watch\|StatelessWidget\|ConsumerWidget" lib/` → no hits.
Rebuild-storm / missing-`const` / non-builder-list findings do not apply here;
they belong to the app-package mappers.

## 5. Reliability risks

### 5.1 `Phd2Client` loses every JSON message split across TCP packets — HIGH confidence, fallback path

`phd2_client.dart:457–462`:

```dart
void _handleData(List<int> data) {
  _lastDataReceived = DateTime.now();
  final buffer = StringBuffer();          // <-- LOCAL, recreated per packet
  buffer.write(String.fromCharCodes(data));
  _processBuffer(buffer);
}
```

`_processBuffer` (465–493) is written to carry a partial trailing line forward —
line 476–479: *"If this is the last line and doesn't end with newline, keep it in
buffer"* → `buffer.write(line)`. But that buffer is the function-local one, which
is garbage as soon as `_handleData` returns. `grep -n "StringBuffer\|_buffer" phd2_client.dart`
returns only lines 459 and 465 — **there is no instance-level buffer field**.

Failure: any PHD2 JSON-RPC frame that arrives split across two TCP reads (routine
for `get_star_image`, whose base64 payload is kilobytes) is dropped. The first
fragment fails `jsonDecode` and is logged at level 900; the second fragment fails
too. The matching `Completer` in `_pendingRequests` never completes and the
caller hangs until the 30 s timeout at `phd2_client.dart:692–698`.

**Fix:** promote the buffer to a field (`final StringBuffer _rxBuffer = StringBuffer();`),
never clear it wholesale, and use `utf8.decode(data, allowMalformed: true)` with
a running decoder instead of `String.fromCharCodes` (which also mangles any
non-ASCII byte — line 460).

### 5.2 `phd2AutoSelectStar` has an inverted native guard — HIGH confidence

`guiding_operations.dart:544–552`:

```dart
Future<void> phd2AutoSelectStar() async {
  if (_nativeAvailable) {
    _nativeBridgeRequired('phd2AutoSelectStar');   // throws "requires the native bridge"
  }
  if (_phd2Client == null || !_phd2Client!.isConnected) { … }
```

Every other guard in the package is `if (!_nativeAvailable)`. Verified unique:
`grep -n -B1 "_nativeBridgeRequired(" bridge_stub/*.dart | grep "if (_nativeAvailable)"`
matches only `guiding_operations.dart:545`.

`_nativeBridgeRequired` returns `Never`, so on any build where the native library
loaded — i.e. every shipping build — this method throws
`UnsupportedError('Operation "phd2AutoSelectStar" requires the native bridge.')`,
which is the exact opposite of the truth. There is no
`apiPhd2AutoSelectStar` in the generated API (`grep -rn "AutoSelect" lib/src/api/`
→ no hits), so "unsupported with native" may be the intent — but the message
lies. Latent today: `NativeBridge.phd2AutoSelectStar` has no callers (§3.2).

**Fix:** either implement the native path, or throw
`UnsupportedError('phd2AutoSelectStar is only available on the Dart PHD2 fallback client')`.

### 5.3 `ImageStats.mad` is populated with the standard deviation

`storage_and_image_operations.dart:189–196`:

```dart
return ImageStats(
  …
  stdDev: native.stdDev,
  mad: native.stdDev,     // <-- MAD set from stdDev
);
```

The `ImageStats` class (`bridge_stub.dart:228–244`) declares `mad` and `stdDev`
as distinct fields. For a star field these differ by roughly 1.48×; any threshold
tuned on MAD would be wrong. Currently latent — `NativeBridge.apiGetImageStats`
is in the zero-caller list (§3.2) — but if the wrapper survives the §2.1 cleanup
this must be fixed or `mad` removed.

### 5.4 `discoverAlpacaServers` mutates its result list after returning it

`alpaca_client.dart:127` fires `unawaited(_tryLocalPorts(servers));` and then
`await Future<void>.delayed(timeout);` (line 130) before `return servers;` (133).
`_tryLocalPorts` (148–173) probes three ports with a 500 ms timeout each and
appends to the *same* list.

`discoverAllAlpacaDevices` (219–231) then does
`for (final server in servers) { await getAlpacaDevices(server); }` — an
`await` inside a `for-in` over a list another future may still be appending to.
If any localhost probe outlives the caller's timeout (2 s from
`discovery_operations.dart:339–341`, vs a worst case of ~1.5 s + scheduling for
`_tryLocalPorts`), the iteration throws `ConcurrentModificationError`.

Timing-dependent, not deterministic — flagged as a race, not a guaranteed bug.
**Fix:** `await _tryLocalPorts(servers)` (it is already bounded by three 500 ms
timeouts) or have it return its own list and merge after the delay.

### 5.5 `NativeBridge.dispose()` permanently breaks the process-wide singleton

`storage_and_image_operations.dart:239–242` is `void dispose() { _eventController.close(); }`.
`_eventController` is a `final` field on the process-wide singleton
(`native_bridge_state.dart:5, 13–14`) and is never reassigned. After `dispose()`,
every `_eventController.add(...)` — `runtime_operations.dart:60`,
`connection_operations.dart:119/220/338/446`, `guiding_operations.dart:129/152`,
`equipment_operations.dart:637/650` — throws `StateError: Cannot add event after closing`,
and `init()` cannot recover because `_initialized` is also never reset.

Latent: `NativeBridge.dispose` has no callers (§3.2). **Fix:** delete `dispose()`
along with the rest of §3.2, or make it reset `_initialized` and recreate the
controller.

### 5.6 Fire-and-forget async in `Phd2Client`

* `phd2_client.dart:365` — `_reconnectWithBackoff();` called from the synchronous
  `_handleConnectionLost()` with the future discarded. The body is fully wrapped
  in `try/catch/finally` (377–436) so nothing escapes, but the reconnect is
  unobservable and untestable.
* `phd2_client.dart:305` — `Timer.periodic(heartbeatInterval, (_) => _sendHeartbeat())`
  discards the future. `_sendHeartbeat` catches `on Exception` only (line 341);
  a non-`Exception` `Error` (e.g. a `TypeError` from a malformed PHD2 reply
  inside `_sendRequest`) escapes as an unhandled async error in the root zone.
  Widen to `catch (e)` or `on Object`.
* `guiding_operations.dart:149` — `unawaited(_phd2Client?.disconnect() ?? …)`.
  Explicit and intentional; noted only for completeness.

### 5.7 Swallowed errors worth knowing about

* `discovery_operations.dart:82–89` — `apiDiscoverIndiAtAddress` returns `[]` on
  any failure, so a wrong host/port and an unreachable server are
  indistinguishable from "server has no devices". (Dead per §2.3.)
* `discovery_operations.dart:180–190` — `_parseIndiDevices` returns whatever it
  parsed on XML failure, with a comment noting the regex fallback deliberately
  adds nothing. Silent partial results.
* `discovery_operations.dart:560–562` — `.catchError((e) {})` per host in the
  subnet scan. Intentional.
* `alpaca_client.dart:111–113`, `169–171`, `206–213` — malformed discovery
  responses and dead ports are swallowed silently.
* `connection_operations.dart:466–475` — `isDeviceConnected` falls back to the
  Dart `_connectedDevices` map when the native query throws, so a native failure
  is reported as the last-known state rather than as an error. Deliberate
  (comment at 472) but worth a second look given the cry-wolf history.

No `unwrap`/`expect`/`panic` applies — this subsystem is Dart-only.
